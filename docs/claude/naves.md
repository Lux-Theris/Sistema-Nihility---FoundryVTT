# Sistema de Naves (Porte, Módulos, Energia, cascata, Tripulação, Reparo)

> Parte do guia do projeto. O índice e as regras que valem em todo lugar estão no `CLAUDE.md` da raiz. Quando o texto diz "abaixo"/"acima" ou cita uma seção que não está aqui, procure-a pelo índice.

## Sistema de Naves (Overhaul de Porte/Módulos/Energia)

Nave Espacial (`type: "starship"`) e Veículo Terrestre (`type: "vehicle"`) both extend `ShipSystemsDataModel` (`module/starship/starship-model.js`) — a shared base with Porte, Módulos, Grid de Energia, cascata de dano e bônus de combate, so the two types are mechanically identical except Vehicle has its own Porte list and additionally has `speed`/`fuel`/`parts` (plain `type: "item"` gear, distinct from `starship_module`). Porte (`shipSize`) is GM-only editable in the header (`{{#unless isGM}}disabled{{/unless}}` on the `<select>`, same pattern as Nível). **Portes are editable catalogs, one per kind** (`shipSizesData`/`vehicleSizesData`, `getVesselSizes(kind)`, defaults `MEU_SISTEMA.DEFAULT_SHIP_SIZES`/`DEFAULT_VEHICLE_SIZES`, editors in `apps/vessel-catalogs-config.js`), ordered small → large; each row carries what used to be hardcoded per-size tables: `rank` (max Módulo size, Motor reference, tractor scale), `weaponBudget`, `distributorBaseline`, `conduitCapacitor`, `move`, `evasion`, `massReference`. Read them through `system.vesselSize` (→ `vesselSizeFor(kind, id)`, which falls back to the default row of the same id and never breaks a ship whose Porte was deleted). With no saved catalog, ship Portes are seeded from the old `shipMove*`/`shipEvasion*` feature options (still registered, marked `legacy` so `FeatureConfigApp` hides them). The Porte → Escala map stays in the Escalas app. Classes carry an optional **size range** (`minSize`/`maxSize`, `sizeFitsClass`/`describeClassSizeRange`, pure/tested): the header selects offer only fitting combinations (plus the current value), a `preUpdateActor` hook refuses a *change* to an out-of-range combination, and a ship already out of range is left alone with a GM-only warning.

**Categorias personalizáveis e Funções**: `category` is now the id of an entry in an **editable catalog** (`moduleCategoriesData`, `getModuleCategories`, editor `apps/vessel-catalogs-config.js`), with no fixed `choices`. What the code understands is the category's **Função** (`MEU_SISTEMA.MODULE_ROLES`: power, storage, distribution, shield, propulsion, ftl, armor, weapon, utility — read through `moduleRole(categoryId)`), and how several modules of the same Função combine belongs to the Função, not the category: power/storage/shield/propulsion/armor **sum** (two warp cores, impulse + maneuvering thrusters — acceleration and rotation add up), ftl/weapon are **independent**, distribution is **single** (only the first online one counts — adding two would double the transfer ceiling), utility has **no mechanics** (Comunicações, Defletor… only HP, consumption and a granted Skill). `ShipSystemsDataModel.modulesByRole`/`sumRoleStat` are what derived data reads; `reactorModule`/`shieldModule`/… now return the *first* module of that Função (for names on the sheet), `armorModule` the armor absorbing right now (several armors take damage one at a time, most damaged first, and `casco` is their sum). Presets are indexed by Função (`MODULE_ROLES[role].presetKey` → the old `MODULE_SIZE_PRESETS` rows). The default catalog keeps the **same 9 ids**, so saved ships work unchanged; a category id missing from the catalog falls back to its default role or to utility — never breaks the ship. **Vagas** (`slots`, 0 = no count limit) replace the slot-único list: `checkSingleSlotAvailable` counts per category against `categorySlotLimit(category, vesselClass)` (pure, tested). **Classes** (`shipClassesData`/`vehicleClassesData`, separate lists, `system.shipClass`, GM-only select in the header) multiply evasion, movement and weapon space, cap the weapon size and override vagas per category — "parrudo" comes from extra Blindagem/Escudo vagas; changing a class never removes installed modules. **Prioridade de energia** is a **per-ship queue of named groups** (`system.powerGroups`, `[{id, label}]` in order; read through `powerGroupList` → `resolvePowerGroups`, which returns the five default groups `p1…p5` — Essencial/Alta/Normal/Baixa/Mínima — while the list is empty). Each Módulo points at a group with `powerGroup` (id); `powerGroupIndex` (pure, tested) resolves it, falling back to the old 1–5 `powerPriority` number (`p${n}`, through `powerPriorityGroup`: 0 → 1, anything outside 1–5 → 3) and then to the middle group — so ships saved before the queue keep every Módulo where it was, and a Módulo brought from another ship lands in the middle. It is the crew's decision (`canAdjustThrottle`), not a factory spec, so it is not on the Módulo sheet. Edited in the ship sheet's **Prioridade** tab (the owner's design, board 5 of the "Grid de Energia — Repaginada" artifact): one card per group with a feed bar above the name (blue = 100%, yellow up to the fed % + striped red rest, all red = nothing), up/down/rename/delete (`movePowerGroup`/`removePowerGroup`, pure: deleting sends its Módulos to the next group, or the previous when it was the last; the queue never empties) and Módulos dragged between cards (own drag type, the card's drop stops propagation so `_onDropItem` never sees it). The "Pn" chip on each module row opens a group selector (`_openPowerGroupMenu`, a menu in `<body>`, closed on pick/Esc/outside click/re-render). `fundByPriority` (pure, tested) takes the group **position** and funds the first group whole, then the next…; when what is left doesn't cover a group, **every Módulo of that group gets the same fraction** and later groups get nothing. A Módulo whose group gets **nothing** is `isPowerStarved`: shown as "desligado · sem energia" and weapons can't fire, but its saved `status` stays `online` on purpose — it comes back by itself when energy reaches its group, and "switched off by the crew" stays distinguishable. The power focus buttons (`applyPowerFocus`) move the focused Função's Módulos to the **first** group and remember where they came from in the `powerFocusMoved` flag (`focusGroupAssignments`, pure), so changing focus or Equilibrado puts them back; choosing a group by hand drops the Módulo from that memory.

**Card do Grid de Energia** (same artifact, boards 1–3): each chain node says *why* it is what it is (Vida of the Reator/Distribuidor/Bateria when damaged — `transferCapacityIntact` gives the "25 de 800" —, generation reserved by Active Skills), the "gargalo" badge only appears on the node actually holding the demand back, and the bar shows where this round's energy comes from — Reator, reserve, missing (`powerBudget`, pure, tested: the same arithmetic as `applyPowerGridTick`, predicted) — so its % matches the per-module "recebendo X%". A forecast line says how many rounds the reserve lasts or how long until it is full. The old "Recalcular Grid de Energia" button ran a real round of `applyPowerGridTick` (spending the reserve on every click); it is now "Passar uma rodada de energia", GM-only. **Tripulação**: `crewMembers[].role` is an id from the `crewRolesData` catalog, meaning only "who is at which post"; **any** crew member can run the whole ship, which works because `syncShipOwnershipToCrew` (`starship/crew-ownership.js`, called with every crew change) gives OWNER on the ship to the users who own a crew member (tracked in `crewGrantedOwners` so leaving the crew revokes only what the crew granted); each crew member changes their own post.

**Módulos** (`StarshipModuleDataModel`, `item-models.js`) are `type: "starship_module"` Items with a `category` (an id of the catalog above) and a `moduleSize` (Compacto→Colossal, `MEU_SISTEMA.MODULE_SIZES`) that reuses the exact same scale for Arma's own Porte. Three install rules run in a `preCreateItem`/`preUpdateItem` hook pair in `nihility-rpg-system.js`: **Vagas** (`checkSingleSlotAvailable`, see above), Porte compatibility (`checkModuleSizeCompatibility` — a Módulo's `MODULE_SIZE_RANK` can't exceed the `rank` of the ship's Porte row) and Arma's space budget (`checkWeaponBudget` — every installed weapon consumes `MODULE_SIZE_RANK + 1` units against `weaponSlotBudget`, a getter on `ShipSystemsDataModel` that reads the Porte row's `weaponBudget`, plus the Classe's `maxWeaponSize`). The old fixed list `MEU_SISTEMA.STARSHIP_SINGLE_SLOT_CATEGORIES` still exists in `constants.js` but the install rule no longer reads it — Vagas replaced it. `reactorModule`/`shieldModule`/etc. are the getters everything else reads instead of tracking an id by hand.

**Presets and auto-fill**: `MEU_SISTEMA.MODULE_SIZE_PRESETS[category][moduleSize]` + `MODULE_HP_BY_SIZE[moduleSize]` (config.js) are suggested stats, not enforced values — `getModuleSizePreset(category, moduleSize)` (config.js) returns them pre-flattened as `"system.field": value` pairs ready for `.update()`/`createEmbeddedDocuments()`. Three call sites share this one source of truth: `NihilityItemSheet#_onModulePresetChange` (item-sheet.js) re-suggests stats when the GM changes Categoria/Porte in the editor — but only overwrites a field still at its schema default, never a hand-edited value (`fieldDefaults` map handles the few fields whose default isn't `0`/`""`, e.g. `transferFactor`/`warpFactor` default to `1`, `hp.value`/`hp.max` default to `20`); `TabbedActorSheetV2.onItemCreate` (starship-sheet.js) seeds a freshly-created Módulo with its Standard-tier preset immediately; `generateVesselFromAI` (ai-generation.js) does the same for AI-generated ships — the AI only ever picks category/moduleSize/name/description, never invents a stat number. Every capacity-like preset field scales by `MEU_SISTEMA.MODULE_SIZE_MULTIPLIER` (×1/2/4/8/16 per Porte, chosen specifically so a Porte bump also doubles that Módulo's power draw — the Grid strain this creates is what discourages casual swap-to-bigger-Módulo, not a currency cost); percent-capped and time-based fields (Penetração/Redução/Recarga/Carga) intentionally do **not** follow that curve (a doubling Recarga every tier would make big weapons unusable) and are hand-tuned per tier instead.

**Energia** (Elite Dangerous-inspired Reator→Distribuidor→Bateria chain): every Módulo has `powerAllocationPercent` (throttle, no ceiling) and `powerPriority`. `ShipSystemsDataModel.totalConsumption` sums `powerConsumption × powerAllocationPercent/100` across online Módulos; `transferCapacity` is the Distribuidor's teto for the whole ship (`baseline(Porte) × distributorModule.system.transferFactor`, baseline = the Porte row's `distributorBaseline`); `powerShortfall` is a **never-persisted** getter, memoized for one data-prep cycle (`#shortfallCache`), that — only when `totalConsumption` exceeds `min(reactorOutput, transferCapacity) + capacitor.value` — funds online Módulos by priority group (`fundByPriority`, see above) and returns the fraction each one actually gets this instant (`powerRatioFor(module)`). `prepareDerivedData` runs in two explicit phases because of that cache: **Fase A** settles the shortfall's *inputs* (Reator output, Capacitor max, and the Capacitor value clamp), **Fase B** then reads a stable shortfall for everything derived from it (Escudo, Motor…). The cache is invalidated at the start of the prep and again between the two phases — keep that second invalidation if you touch this, or Fase B freezes on a half-built Fase A state. `effectiveModuleStat(module, field)` (the one helper basically everything derived reads) multiplies a Módulo's base stat by both its own throttle ratio AND this starvation ratio — this is how Reator's `reactorOutput`, Escudo's `shieldCapacity`/`shieldRegen`, Motor's `acceleration`/`rotation` (→ `StarshipDataModel.maneuverability`/`VehicleDataModel.speed`, no longer free-typed fields, purely derived), and Bateria's `batteryCapacity` (→ `powerGrid.capacitor.max`) all end up scaled — running short on power isn't a UI warning only, it's mechanically real the instant you read any of these. Reator/Distribuidor/Bateria don't get a throttle control in the item editor UI (their fields aren't meaningfully "overclockable" the same way); Reator instead reuses the same `powerAllocationPercent` field as its Under/Overclock — Underclock (<100%) never damages, any Overclock (>100%) does, no tolerance band, unlike every other category's threshold (`MEU_SISTEMA.OVERLOAD_THRESHOLD_REACTOR`/`_SHIELD`/`_DEFAULT`).

**Sobrecarga** (`tickStarshipModuleOverload`-equivalent logic in `module/starship/starship-power.js`'s `tickStarshipPower`, called from the same `updateCombat` hook as the Skill ticks): a Módulo whose `powerAllocationPercent` exceeds its category's threshold takes `(excess/100) × hp.max × MEU_SISTEMA.OVERLOAD_DAMAGE_PERCENT_OF_MAX_PER_ROUND` per round (`0.5`, tuned to ~5% of max HP per round per 10 points of excess). Any Módulo whose `hp.value` hits 0 force-offlines itself regardless of cause (overload here, combat damage, manual GM edit) and can't be manually re-toggled online below `MEU_SISTEMA.MODULE_RESTART_HP_THRESHOLD_PERCENT` (15%) of `hp.max` — checked both in this tick and in `TabbedActorSheetV2.onToggleModulePower` (`moduleCanRestart()` from `starship-power.js`). Arma is exempt from this whole mechanic (see below) and so are Bateria/Distribuidor (no throttle to overclock in the first place). The same tick also decrements Arma's `cooldownRemaining` and FTL "Salto"'s `chargeRemaining`, runs `applyPowerGridTick()` last so the Capacitor actually charges/discharges during combat (it used to move only when someone clicked the manual button on the sheet — which stopped being acceptable once the Capacitor became the pool that pays Skill costs), and handles Escudo's Regen/Recarga (`computeShieldTickPatch`): `rechargeRemaining > 0` blocks regen entirely (0% protection during Recarga), set by the damage cascade the instant `shields.value` hits 0; once it reaches 0 the Escudo resumes regenerating `shieldRegen`/round toward `shields.max`.

**Cascata de dano** (Escudo → Casco → Integridade Estrutural). It is the one part of ship damage that writes itself with no confirmation — the three layers are bookkeeping the GM would otherwise redo by hand every hit; Personagem damage instead stays a number in chat until someone clicks Aplicar. `rollSkillDamage`/`rollSkillDamageArea`/`fireStarshipWeapon` branch to it for any `isShipLike(targetActor)`. `hull` is labeled "Integridade Estrutural" in the UI (the definitive name, not "Estrutura"). The whole computation is `resolveShipCascade` (damage-rules.js, pure, tested) — Evasão → "Preparar para impacto" (`incomingDamageReduction`, not vs. Absoluto) → Absoluto straight to Integridade (whole, no layer %) → Trait bonus → Escudo (penetration minus `shieldPenetrationResist`: best online shield module's `penetrationResist` + class `shieldPenResist` − "resistência baixa") → Casco (armor reduction, then penetration minus `cascoPenetrationResist`) → Integridade. Each layer applies the element's **layer %** (`layer` element effect; negative = weakness) through `absorbLayer`: the layer suffers `base × multiplier` and what it holds is counted in the hit's currency, so what leaks continues without that layer's %. The legacy "Dano extra em Escudo" is folded into the shield multiplier. `applyStarshipDamageCascade` only writes: shield value/recharge, `damageCasco`, and Integridade via `applyStructuralDamage` or, with **"Mirar num sistema"** (`promptTargetModule`, single-target only; ask + share are world settings read by `getShipTargetingConfig`), `applyTargetedStructuralDamage` (`splitTargetedStructural`, pure). **Ship system effects** (element effect types `moduleDisable`/`energyDrain`/`resistanceDown`) and element Conditions against ships only roll with the part that **passed the Escudo**, chance reduced by `hardeningFor(module)` (module `hardening` + class `hardening`, `hardenedChance` pure); they live in the Actor flag `shipEffects` (`systemEffects` getter; same kind refreshes to longest/strongest), are read by derived data (reactor output, penetration resists, armor reduction, brace) and tick down in `tickStarshipPower` (`tickShipSystemEffects`; a disabled module comes back online if it can restart). New ship Effect targets act immediately (`SHIP_INSTANT_TARGETS`: restore Escudo, Casco/Integridade ± , brace %), and `shipCasco`/`shipHull` also accept Periódico (damage over time uses the layer %; positive = repair via `repairModules`); a Condition's Vida tick landing on a ship becomes a `shipHull` tick.

Penetração in that cascade comes from the attacking weapon (`shipWeaponPenetration(sourceActor, weaponModule)` — `effectiveModuleStat(weaponModule, "penetration")` plus `combatBonuses.weaponPenetrationFlat/Multiplier` from aprimoramento Skills): at the Escudo and Casco stages the penetrated fraction always leaks forward, the rest tries to be absorbed by that layer. Casco's `armorReductionPercent` (from the `armor` Módulos, whose `hp.max` feeds `casco.max`) reduces what reaches it **before** its own Penetração split — but only while `casco.value > 0`: a Casco worn through stops reducing anything.

**Armas** are native to the Módulo now (Fase 5 of the overhaul), not only a Skill a Módulo grants: `damageFormula`/`penetration`/`cooldownRounds`/`cooldownRemaining` live directly on a `category:"weapon"` Módulo, fired via the `fireWeapon` action → `fireStarshipWeapon()` (`ship-damage.js`), which rolls the formula, scales it by throttle+power-starvation (same `effectiveModuleStat`-style math) and `combatBonuses`, then runs the same damage cascade using that specific weapon's Penetração. Arma's own overload rule diverges from every other category on purpose: throttle above 100% never damages the Módulo — it scales Dano/Penetração up **and** scales `cooldownRounds` by the same ratio (rounded up, minimum 1), so overclocking a weapon hits harder but reloads slower, rather than risking destroying it. `grantsSkill` still works independently for non-damage abilities a Módulo wants to grant (Casco/Utilidade modules commonly use this) — it was never replaced, just no longer the only way an Arma deals damage. FTL (`category:"ftl"`) has two mutually-exclusive sub-types sharing the one slot (`ftlType: "warp"|"jump"`): Dobra (`"warp"`, the default) is continuous propulsion with no cooldown (`warpFactor`, subject to the normal throttle curve); Salto (`"jump"`, meant to be rare/narratively gated by the GM, not mechanically restricted) uses `jumpRange` + `chargeTime`/`chargeRemaining` (same cooldown-countdown pattern as Arma).

**Ajuste manual do Mestre**: the character sheet's `.vital-adjust-popover` pattern (a toggle button opening a small +/- input) was generalized in `starship-sheet.js` into `toggleModuleVitalAdjust`/`adjustModuleVital`, driven entirely by `data-scope` ("actor"|"item")/`data-item-id`/`data-field`/`data-max-field` on each button instead of a hardcoded `vital` name — the same two actions cover Escudo/Casco/Integridade Estrutural pools on the Actor, `hp` on any individual Módulo, Escudo's `rechargeRemaining`, and Arma's `cooldownRemaining`, all GM-only (`{{#if isGM}}`). Each `<li>` wraps its visible row in an inner `<div class="item-row">` (not the `<li>` itself) specifically so the popover can be a second block-level sibling inside the same `<li>` without becoming an invalid direct `<ol>` child — don't move `.item-row`/`data-item-id` back onto the `<li>` when touching this template, the `.closest(".item-row")` lookups in every row action depend on it staying on the inner `div`.

**Tripulação** (`crewMembers` in `shipSystemsSchema()`, `crewActors` getter): a list of `{actorUuid, role}` on the Nave/Veículo — the Personagem documents stay independent, only the *association* lives here. `crewActors` resolves them with `fromUuidSync` (a Data Model getter can't be async) and silently drops entries whose Actor was deleted without rewriting the stored list — reading must never mutate. GM-only to edit, via drag&drop onto the "Tripulação" tab of the ship sheet (`_onDropCrewMember`/`onRemoveCrew`/`_onChangeCrewRole` in `starship-sheet.js`). Every crew change must also call `syncLibraryOwnershipToCrew()` (`pad/pad-library.js`) so someone who leaves the crew loses access to the ship's PAD Library. The inverse lookup ("which ships does this Personagem crew?") can't be a Data Model getter at all — it's a cross-Actor scan, so it lives in `pad/pad-crew.js` as `findCrewedShipsForActor()`.

**Alvos de Efeito por tipo de Ator — `resolveEffectChange(entry, targetActor)`** (`skills/effect-targets.js`) turns an effect entry into the Active Effect change *for that target*: the same target lands on different fields depending on the Actor type, and a target that makes no sense for that type (Força on a ship, a ship system on a person) is **refused with a note in the chat summary** instead of silently creating an effect that does nothing, which is what used to happen. Targets are grouped in `MEU_SISTEMA.EFFECT_TARGET_GROUPS` (Atributos / Vitais / Arma / Nave), rendered as `<optgroup>`s by `getEffectTargetGroups` in both effect editors. **Aprimoramento de arma**: `weaponDamage` (Fixo/Multiplicador), `weaponElement` (OVERRIDE with the entry's `elementId` — replaces the elements of every equipped weapon while it lasts), `weaponMagic` and `weaponAbsolute` (ADD counters, > 0 = on, so several sources stack and removing one doesn't cancel the others). On a Personagem they write `system.weaponBonuses` and are read by `useWeaponAttack` (only equipped weapons attack, so "equipped weapons" is automatic); on a ship they write `combatBonuses` and are read by `fireStarshipWeapon`. **Ship system boosts** `shipShieldCapacity`/`shipShieldRegen`/`shipReactorOutput`/`shipPropulsion` are summed percentages in `combatBonuses.*Percent`, applied through `bonusFactor()` in `prepareDerivedData`/`engineRatioFor`; a crew member's Skill can target the ship with them.

**Mana em 0** (`shutdownActiveSkillsOnDepletion`, from an `updateActor` hook on the designated GM): whenever a Personagem's Mana reaches 0, for any reason, **every** Active Skill of theirs is switched off at once (they stop costing); the effects they were holding — including on other Actors, e.g. a ship a crew member boosted — disappear at the **start of that Actor's next turn** in a started combat (`pendingUpkeepRemoval` flag, processed by `processPendingUpkeepRemoval` in the `updateCombat` hook), or immediately out of combat. A ship's Capacitor reaching 0 does not trigger it.

**Bônus de Nave vindos de Skills**: `MEU_SISTEMA.EFFECT_TARGETS` includes two ship-only targets, `shipWeaponDamage` and `shipWeaponPenetration` (listed in `SHIP_EFFECT_TARGETS`). They don't map to a `buffDelta` path like the other targets do — each stores Flat and Multiplier in *separate* fields under `system.combatBonuses`, so `resolveEffectTargetPath(entry)` picks the field by the entry's `modifierType` (`"flat"` → `ACTIVE_EFFECT_MODES.ADD`; `"multiplier"` → `MULTIPLY`, where `amount` is read as a percentage, so 20 becomes the factor 1.20 — that's why `weaponDamageMultiplier` initialises to 1 and not 0). `applyShipWeaponBonus`/`shipWeaponPenetration` apply Multiplier first, then Flat.

**Foco de energia, Ações da Nave e Raio Trator** (`starship-power.js`): `applyPowerFocus(ship, focus)` sets throttle/priority only on shield/weapon/propulsion modules (focus → P1 at `shipFocusBoost`, capped at the role's overload threshold; others → P3 at `shipFocusCut`; balanced → 100%/P3) and records the `powerFocus` Actor flag; the ship sheet and the PAD Nave screen both call it. The "Ações da Nave" block uses the ship system effects list (`systemEffects` flag): `brace` (`shipBracePercent`, 1 round), `transferCapacitorToShields`, `requestShipRepair(ship)` (the macro path still needs exactly one ship on the scene) and `endShipSystemEffect`. The tractor (`role: "tractor"`) writes a `tractor` system effect on the target (`percent` from `tractorHold`, pure/tested) plus a `tractorTarget` flag on the module, through the `engageTractor`/`releaseTractor` relay actions (strength recomputed GM-side); it has no rounds and is dropped in `tickShipSystemEffects` once the source module is no longer online. `movementCells` multiplies by `1 − tractor%`.

**Reparo** (`module/starship/starship-repair.js`, exposed as `game.nihility.requestShipRepair()` — one of the system's public macro APIs alongside `openAssistant()`): a player picks a Nave/Veículo they can Observe, a target (any Módulo's `hp`, or the Actor's Escudo/Casco/Integridade Estrutural pool), and who repairs — **the ship's crew** (`crewActors`, all of them, the Engineering post first under its own optgroup and starred; a role counts as Engineering when its id is `engineer` or its label contains "engenh"), falling back to the user's own characters on the scene when the ship has no crew; a repairer on the Engineering post restores more HP: the `shipRepairEngineerFormula` world setting (default `1d6`, `getShipActionConfig().repairEngineerFormula`, validated with `Roll.validate`) is added to `REPAIR_ROLL_FORMULA` in "Restaurar Vida" — decided at request time and stored as the `engineerBonus` string in the card flags (the Destreza roll gets no bonus); the engineer is stored by `engineerUuid` (unlinked crew tokens), with `engineerId` kept for old cards; this whispers a chat card to the GM with a free modifier field. "Rolar Destreza" (GM-only) rolls `rollAttribute(engineer, "dexterity", {extraFlat: modifier})` — same escalating-dice formula as any other attribute roll — and the GM judges success by eye, same philosophy as the rest of the system (no DC baked in). "Restaurar Vida" (GM-only, appears after the roll) then rolls `MEU_SISTEMA.REPAIR_ROLL_FORMULA` (`"2d6"`) and applies it clamped to the target's max — the same flat formula regardless of target size, so a bigger Módulo just needs more successful attempts rather than a size-scaled roll.
