# Fichas e janelas (ApplicationV2) e o redesenho da ficha de Item

> Parte do guia do projeto. O índice e as regras que valem em todo lugar estão no `CLAUDE.md` da raiz. Quando o texto diz "abaixo"/"acima" ou cita uma seção que não está aqui, procure-a pelo índice.

## Sheets and Apps — all ApplicationV2 now

Every sheet/app in this system was migrated off the classic AppV1 API (the same framework mismatch — `html.querySelectorAll` called on what is actually a jQuery object under AppV1 — once broke `nihility-menu.js` outright; ApplicationV2 hands you a plain `HTMLElement` instead, so that whole bug class is gone). The shared conversion pattern, if you're adding a new sheet/app or touching an existing one:
- `class X extends foundry.applications.api.HandlebarsApplicationMixin(Base)`, where `Base` is `foundry.applications.api.ApplicationV2` (plain apps: menu, AI assistant, config editors) or `foundry.applications.sheets.ActorSheetV2`/`ItemSheetV2` (Document sheets).
- `static DEFAULT_OPTIONS = {...}` (object literal, not a getter) with an `actions: { actionName: MyClass.#onActionName }` map — referencing a `static async #onX(event, target)` declared later in the same class body works fine (private static methods are attached before static field initializers run, regardless of textual order). Handlers run with `this` bound to the app instance; `target` is the element carrying the matching `data-action`.
- `static PARTS = { body: { template: "..." } }` — every part's template needs **exactly one root HTML element** (`Template part "body" must render a single HTML element` if not) — the old AppV1 templates that used to open with a bare `<form>` now need that as their single wrapping tag (or a plain `<div>`, for non-document apps that don't need `tag: "form"`).
- `getData()` → `async _prepareContext(options)` (call `super._prepareContext(options)` first and extend that object — don't return a fresh one). `activateListeners(html)` + jQuery `html.find(...)` → `data-action` attributes in the template, or for non-click events (a `change` listener, drag&drop) manually wired in `_onRender(context, options)` against `this.element.querySelector(...)` (plain DOM, not jQuery).
- **Tabs and parts (Onda 5, 1.108.0): the three Document sheets (Personagem, Item, Nave/Veículo) use the native ApplicationV2 `PARTS` + `TABS`** — follow the same pattern in any new tabbed sheet/app:
  - `static PARTS`: header, the tab nav, then **one part per tab** (`templates/parts/<ficha>-<aba>.hbs`; the Item sheet has one part per (type, tab), picked by `PARTS_BY_TYPE`). Each tab part's single root is `<section class="tab sheet-body {{tabs.<id>.cssClass}}" data-group="primary" data-tab="<id>">`, with `scrollable: [""]`. The old outer `<div class="nihility-sheet …">` cannot wrap sibling parts, so those classes go on `.window-content` (`window.contentClasses` on the ship sheet; `_renderFrame` on the Personagem and Item sheets, where a class depends on the document).
  - `static TABS = {primary: {initial}}` plus `_getTabsConfig("primary")` returning the tabs that exist now (Item type via `tabsFor`; Anatomia and Inventário toggles, ficha enxuta and modo criação on the Personagem; Tripulação only with the ship PAD). `_configureRenderParts` drops the parts of absent tabs. The active tab lives in `this.tabGroups.primary`; to force one, set it before `render` (or `changeTab` after) — `_prepareContext` falls back to the first/initial tab when the stored one no longer exists.
  - The nav links carry `data-action="tab" data-group="primary" data-tab="<id>"` inside a `.tabs` container (in-content links that jump to a tab use the same attributes). **Trap:** the core `_onClickTab` reads `event.target.dataset.tab`, so a click on a child (count badge, led) did nothing — the sheets override `_onClickTab` to use `event.target.closest("[data-tab]")`.
  - Switching tabs no longer re-renders (core `changeTab` toggles `.active`; core CSS hides `.tab[data-tab]:not(.active)`), so open popovers and screen state survive. Context only one tab uses is prepared in `_preparePartContext` for that part. `_onRender` listeners must be idempotent (the Item sheet's `bindOnce`) or bound per `options.parts`, since a partial render keeps the other parts' elements. A part dropped by `_configureRenderParts` is not removed from the DOM by the core — the Personagem sheet removes stale Inventário/Anatomia sections in `_onRender`.
  - **Editor in a hidden tab:** `<prose-mirror>` measures its toolbar when it mounts; mounted inside a `display:none` tab everything measures 0 and the toolbar loses buttons (color, lists, image, link). `helpers/sheet-tabs.js`: `markVisibleEditorParts` in `_onRender` marks parts drawn while visible, and the sheets' `changeTab` override calls `refreshEditorOnTabShow`, which re-renders only that part the first time it is shown. A sheet whose `_onRender` binds listeners on the whole element must skip that binding on this editor-only partial render (the ship sheet does).
  - Other apps (menu, config editors, PAD) still use the older hand-rolled pattern (`this.activeTab` + a `selectTab` action + `hidden` class); convert them to the pattern above when touching them.
- `Dialog.wait`/`Dialog.confirm` → `foundry.applications.api.DialogV2.wait`/`.confirm` — `buttons` is an array (`[{action, label, default, callback: (event, button, dialog) => value}]`), and the callback reads form fields off `dialog.element` (plain DOM) instead of a jQuery-wrapped `html`.
- Document sheets (`ItemSheetV2`/`ActorSheetV2`) keep the old `submitOnChange` behavior via `form: { submitOnChange: true, closeOnSubmit: false }` — no `form.handler` override needed, the DocumentSheetV2 default already applies the diff to the Document. **Ficha de Item follows the approved redesign** (the owner signed off on the artifact "Redesenho da Ficha de Item" — its boards are the spec; build to them instead of improvising a layout, which is what happened once and had to be redone). Principles: summary chips in the header (`headerChipsFor`), one tab per question (`tabsFor` — the first tab is the one that opens, never Descrição; `count`/`led` show what's inside without opening it), sections `.sec` with a title and a 2–3 column grid, label always above the field, help in a `(?)` with `title` instead of paragraphs between fields (only state that changes what you can do stays as a `.strip`), choices of 2–5 options as a segmented control (radio inputs styled as `.seg`, so `submitOnChange` saves them with no JS), and a field that depends on another lives inside that field's section with a "muda com X" badge. Tabs: **Skill** Geral · Mecânica · Passivos · Sub-Skills · Descrição; **Item Geral** Geral · Arma (led) · Enquanto equipado · Descrição; **Módulo** Especificação (Categoria as tiles showing vagas, Porte as a segmented ruler, one "Parâmetros · Função" section that swaps by role) · Habilidade Concedida · Descrição; **Título** Detalhes · Descrição; **Parte do Corpo** Detalhes · Modificações · Descrição. There is exactly one `<prose-mirror name="system.description">` in the form (the Descrição tab), never two. Effects are cards with a group tag and a sentence built from their own fields; Condição/Ícone stay folded behind "+ Condição" until used (`#openConditionRows`, screen state only). **"Avançado ▸" (backlog K1, 1.77.0; mockup approved by the owner: Design artifact "Avançado nos Editores de Skill", boards 1–3, with two changes asked after a usability search — Periódico stays visible because it changes what Duração means, and a card with nothing advanced shows no line at all):** rarely used fields live in a native `<details class="adv">` at the foot of their own section, never in a separate tab — Custo e ativação (Variar a Mana, Mágica), Apresentação (Gatilho Emocional), Dano (Dano Absoluto, Escala do golpe), and per Effect card (Elemento do tick, Tipo de cura, Elemento do escudo, Escudo mantido, Luz, "Sem Mana para pagar"). `advancedFold(fields, userOpen)` (`helpers/advanced-fold.js`, pure, tested) gives the summary line (`nihility.advSummary` partial): every field's name, an "em uso" badge, and `open` when something inside has a value unless the user opened/closed it by hand in this window (`#advOpen`, screen state; effect keys `eff-<i>` are dropped when an effect is deleted). Fields inside a closed `<details>` still submit. The quick Skill editor (`skill-editor-dialog.js`) follows the same rule: Variar a Mana/Mágica/Animação and Dano Absoluto/Escala at render time, each effect row recomputed by `refreshAdv()` on every change (opens by itself only when the row is built). Because Categoria and Porte are radio groups now, `_onModulePresetChange` reads `:checked` and is bound to every radio. **Array trap:** a form that renders only some fields of array entries (`system.installedMods.0.name`…) makes Foundry build a *new* array from those fields alone, silently resetting every field that has no input on screen. `NihilityItemSheet#_processFormData` runs `mergeSubmittedArrays`, which merges each submitted entry onto the existing one; do the same on any other sheet that renders partial array rows through `name=` inputs.

`module/sheets/*.js` + `templates/*.hbs` are the Actor/Item sheets built this way; `module/apps/*.js` + `templates/apps/*.hbs` are the rest (`NihilityMenuApp`, `AIAssistantApp`, `NihilityPadApp`, the six config editors — three of them (Currencies, Damage Elements, Status Conditions) built by `list-config-app-factory.js`, while `FeatureConfigApp`, `AttributeConfigApp` and `SpeciesConfigApp` are hand-written because their row sets are fixed or nested, see the `config.js` section above —, `skill-editor-dialog.js`'s `openSkillEditorDialog` — a `DialogV2`-based modal, not a full app, used where there is no Item to open yet: Species racial skills, the Skill Point request, granted skills, Sub-Skills and Evolution. The sheet's "+ Nova Habilidade" does **not** use it any more (1.71.0): a small Name + Tier prompt creates the Skill and opens its Item sheet — the approved design and the most complete editor — and the Compendium registration waits for that sheet's first close (`closeApplicationV2`) so it stores the filled-in Skill. The modal's own CSS left-aligns its text (V14's DialogV2 centres it) and styles checkboxes as options, not as faint uppercase headings. The Item sheet's Animação field has "Ver animações" (`Sequencer.DatabaseViewer.show()`, only with Sequencer active) and "Arquivo…" (FilePicker `imagevideo`).


- **Cabeçalho da ficha com Condições (sessão 4, 1.103.1):** a coluna `.resources` (barras, Descansar/Efeitos/Iniciativa e a faixa de chips) tomava a largura do conteúdo em uma linha e empurrava `.header-fields` para ~0 px, e Nível/Tamanho/Fluxo/Traços ficavam sob os botões. Agora `.resources` tem 300 px (a faixa de chips quebra linha dentro dela) e `.sheet-header` quebra em janela estreita (`13-screen-and-combat.css`).
