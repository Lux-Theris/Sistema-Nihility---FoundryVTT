## AI integration and the `ai-helper.js` split

`ai-helper.js` used to be one 1166-line file owning everything from Compendium management to currency conversion to AI generation. It was split (2026-08) into focused modules, each with a single concern; `ai-helper.js` itself is now just ~60 lines that import from all of them and assemble the `AIHelper` object exposed at `game.nihility.ai` — **nothing in the rest of the codebase imports individual functions from `ai-helper.js` anymore, only `AIHelper` itself (only `nihility-rpg-system.js` does even that)**. Import the function you need directly from the module that owns it:
- `compendium.js` — `ensureSystemCompendiums`, `getCompendiumForItemType`, `registerItemInCompendium`. Used by almost everything else in this list. `NIHILITY.COMPENDIUM` declares seven World packs (Skills, Partes do Corpo, Títulos, Itens, Módulos de Nave, Biblioteca do PAD, Grupos do PAD), all created on `ready`; the AI backup pack in `world/world-backup.js` is an eighth that creates itself outside this list. The Itens pack (Item Geral) is fed by AI generation and by the GM by hand, but **not** by the sheet's "+ Novo Item" button (`COMPENDIUM_MANAGED_TYPES` in `actor-sheet.js` leaves `item` out on purpose: that button creates a blank "Novo: item", and registering it would fill the pack with placeholders). `registerItemInCompendium` decides "is this the same Item?" through `itemFingerprint` (name + tier + sorted fusion lineage), not by name alone — two different Skills called "Corte" used to collapse into one entry, and fusion (which registers its sources before consuming them) could then recover the wrong one. Entries created before the fingerprint existed are still matched by bare name, so existing worlds don't suddenly duplicate their whole Compendium. "Criar Item" inside one of these packs is preselected and restricted to that pack's type (`registerCompendiumCreateDefaults`, a chained `CONFIG.Item.documentClass` subclass overriding `createDialog`): Skill is the first Item type in `system.json`, so the Itens pack used to fill with Skills created by accident. That override alone did not catch the creation path in a real world, so the same function adds a `preCreateItem` safety net: a **blank** Item (no `system` data — how the dialog creates it) born in a system pack with the wrong type is cancelled and recreated with the pack's type; an Item dragged/imported with content is never touched.
- `skill-snapshot.js` — `buildSubSkillsFromSources` only. Split out specifically so `skill-economy.js` and `ai-generation.js` could both depend on it without depending on *each other* (see the circular-import note in "Skill mechanics" above) — if you're tempted to inline this elsewhere, don't; keep the one shared copy.
- `skill-economy.js` — Skill creation/lifecycle (fusion, evolution, granted skills, Skill Point economy) — see "Skill mechanics: creation vs. runtime use" above.
- `currency.js` — `convertActorCurrency`, `transferCurrency`. Currency conversion never leaves a fractional amount on the destination currency: `applyWholeCurrencyAmount` (private to this file) recursively cascades any fractional remainder down into the next-lower-`baseValue` currency (careful with this function if you touch it — it was fixed once for a bug where the cascade could land back on the source currency and get overwritten instead of accumulated).
- `voice-of-the-world.js` — `announceVoiceOfTheWorld`, `announceLevelUp`. "Voz do Mundo" is the system's private-announcement channel (level-ups, fusions, new skills, currency transfers) — always sent via `whisper` to GMs + the Actor's owning player(s), never public. Don't make this public without being asked; that's a deliberate design choice, not an oversight.
- `ai-generation.js` — everything that actually talks to an AI provider, routed through `generateJSON()`/`callAIProvider()` (`generateJSON` is private to this file; `callAIProvider` lives in `module/ai/providers.js`, which adapts either OpenAI-compatible Chat Completions or the native Anthropic Messages API — the only place that knows either wire format). Two distinct capabilities:
  - **Create**: `generateActorFromAI`, `generateVesselFromAI`, `generateNoteFromAI`, `generateSkillFromAI`, `generateItemFromAI`, `generateFreeform` — always create a brand-new document. `generateActorFromAI` asks the model for **attribute points**, never for HP/Mana — those are derived, so a generated `hp` would be silently overwritten (it used to be, leaving every AI NPC on zeroed attributes and the HP floor); the Actor is then topped up to full HP/Mana once. `generateVesselFromAI` deduplicates single-slot Módulo categories *before* creating them, because everything goes out in one `createEmbeddedDocuments` call and the `preCreateItem` guard can't see not-yet-created siblings.
  - **Edit in place**: `editDocumentWithAI(doc, instruction)` — sends the doc's current `{name, type, system}` snapshot plus a free-text instruction, expects back a JSON patch restricted to `name`/`img`/`system.*` keys (`sanitizeDocumentPatch` strips anything else, e.g. `_id`/ownership), and applies it via `doc.update()`. Only Actor/Item are supported (not JournalEntry). Driven from `module/apps/ai-assistant.js`'s "Editar Existente" mode, which resolves the drag-dropped target via `TextEditor.getDragEventData`.

**Mechanics in AI-generated content** (`module/ai/ai-mechanics.js`): the model is told the full Skill mechanics shape plus the ids that exist in *this* world (`mechanicsGuide(currentAICatalogs())` — elements, Conditions, attributes, effect targets), and whatever comes back goes through `sanitizeSkillMechanics` / `sanitizeWeapon` / `sanitizeItemBonuses` (pure, tested): unknown ids are dropped, numbers clamped, an invalid dice formula (`foundryFormulaCheck` → `Roll.validate`) turns the Skill descriptive instead of breaking it at use time, a "temporary" Skill with no valid effect becomes "none", ship targets are refused. Used by the standalone Skill generator, NPC/mount Skills, Item generation (weapon + while-equipped bonuses) and the Agent's `propose_skill` (`mechanics` object; `get_system_rules` returns the guide). Before this, every AI Skill came out "Descritiva". Fusion (Única/Ultimate) still gets its mechanics from the consumed Skills' Sub-Skills.

Dependency direction is a DAG, not a cycle: `ai-generation.js` depends on `compendium.js`/`skill-snapshot.js`/`voice-of-the-world.js`; `skill-economy.js` depends on those three *plus* `ai-generation.js` (for the "auto" mode of `fuseSkills`, which asks AI to write a Skill Única/Ultimate); `ai-helper.js` sits on top of everything. If you ever need something from `skill-economy.js` inside `ai-generation.js`, that's a sign the shared piece belongs in a new low-level module (like `skill-snapshot.js`) instead, not a reason to import `skill-economy.js` there directly.

## Agent mode: tool-calling AI assistant

`module/apps/ai-assistant.js`'s third mode ("Agente", alongside the pre-existing "Criar"/"Editar") lets the GM ask for a *mix* of content in one prompt (e.g. "crie 3 skills e 2 personagens") and have the AI ground itself in the actual system state before proposing anything:
- `module/ai/providers.js` — `callAIProviderWithTools`/`appendAssistantAndToolResults` extend the existing single-shot `callAIProvider` with multi-turn tool-calling for both wire formats (Anthropic `tool_use`/`tool_result` blocks vs. OpenAI-compatible `tool_calls`/`role:"tool"` messages) — still the only place that knows either format.
- `module/ai/agent-runner.js` — `runAgentTask` drives the loop: calls the provider, executes whichever tool the model asks for, feeds the result back, repeats until the model stops or `maxTurns` is hit. Never touches the world directly.
- `module/ai/agent-tools.js` — `createAgentTools()` returns the actual tools: read-only ones for grounding (`list_skills`, `list_actors`, `get_system_rules`) and `propose_skill`/`propose_character`/`propose_edit`, which only push an already-normalized, schema-correct document into a `proposals` array — nothing is created yet.
- The app renders `proposals` as a review checklist; only on "Aplicar selecionados" do documents actually get created/edited (via the same `registerItemInCompendium`/`Actor.create`/`sanitizeDocumentPatch` primitives the other AI paths already use).
- Every apply records one entry in `module/world/world-backup.js` (a hidden World Compendium of `JournalEntry`, `recordBatchOperation`/`undoBatchOperation`/`listRecentBatchOperations`) so a whole batch — not just one document — can be undone from the same app. This replaced an earlier `localStorage`-based backup helper that didn't sync between GM/players and only tracked one document at a time; don't reintroduce that pattern.

`module/apps/nihility-menu.js` is the system's single entry point — reachable from `game.nihility.openAssistant()` and the Actor Directory button — and is where every one of these modes gets opened from. It has **four** rail tabs: "Fichas" (an Actor browser with search/type filter, the one tab **players** can use — it lists Actors they own or can Observe) plus the GM-only Configurações Gerais / **Criar com IA** (the old "Assistente de IA" and "Geração Automática" tabs opened the same assistant and listed NPC twice, so they were merged) / Ferramentas de Admin. Configurações Gerais is no longer a grid of loose cards: it is a searchable list in sections (Campanha / Personagem / Combate e Dano / Naves), built in `_settingsSections()`, where each row shows the current state of its catalog ("14 tipos · 4 grupos"), rows of disabled blocks disappear and a footer lists what the campaign turned off. **Regras da Mesa** (`apps/table-rules-config.js`) gathers every world-scoped `config: true` system setting (XP, points per level, vital formulas, initiative…) grouped by subject, read straight from `game.settings.settings`, so a new setting appears there by itself; client-scoped ones (AI, Debug) stay on the native settings screen. GM-only tabs render with a padlock for players rather than disappearing, and are blocked twice — in `#onSelectTab` and again in `#onRunAction`. Every button is wired to real functionality: Economia/Anatomia/Condições open `CurrencyConfigApp`/`SpeciesConfigApp`/`StatusConditionsConfigApp` directly, Títulos opens the world's Títulos compendium browser, the `generate-*` actions route through `AIAssistantApp`'s `initialTask`, `sync-data` re-runs `ensureSystemCompendiums()`, and `export-data`/`import-data` carry **every world-scoped system setting** — all catalogs, the Módulos do Sistema toggles with their fields, and the rule numbers — except the migrations record and the client-scoped ones (the AI key must never travel in a shareable file). Both open a grouped checklist (Catálogos / Módulos do Sistema / Regras); import shows only what would change (JSON compared by content, not formatting) and accepts the old 4-list format. The pure part (`readTransferBundle`, `diffTransfer`, `transferGroup`) lives in `module/core/config-transfer.js` and is tested. **Campaign presets carry content** too (`CAMPAIGN_PRESETS[*].content`, resolved by `presetContent`, pure/tested): Sci-Fi and Misto load the Star Trek–style damage elements and module categories, Fantasia the fantasy elements — replacing those catalogs, which the confirm dialog says explicitly. The Configurações Gerais tab leads with **Módulos do Sistema** (`FeatureConfigApp`) and also exposes Tipos de Dano (`DamageElementsConfigApp`), which used to be registered but unreachable from here. Tabs for blocks the campaign turned off are dropped from the rail entirely (not padlocked like GM-only ones) — "this campaign doesn't use that" reads differently from "you can't touch that" — and the active tab falls back to Fichas if it just disappeared. Every menu action now has a button, including `open-ai-assistant` (card "Assistente Completo", the only route from the menu into the Editar/Agente modes) and `create-macros`, which builds the `game.nihility.*` hotbar macros in the world — idempotent by macro name, and the Repair one is created with `ownership.default: OBSERVER` because requesting a repair is a *player* action.
