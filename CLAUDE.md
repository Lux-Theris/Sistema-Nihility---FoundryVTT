# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Nihility RPG System — a custom Foundry VTT game system (id `nihility-rpg-system`, **requires Foundry V13+**, verified to V14) built for a Fantasia/Isekai + Sci-Fi Arcano campaign. It's a manifest-driven Foundry system: pure static JS/Handlebars/CSS, no bundler and no `package.json` (the test suite runs on Node's built-in `node --test`, with zero dependencies). Foundry loads `module/nihility-rpg-system.js` as an ES module directly.

**Design goal to respect in every change:** the owner runs medieval-fantasy, sci-fi and mixed campaigns from this one system, and wants subsystems to be switchable per world. Anything you add should either sit behind a feature toggle or be small enough not to get in the way when the campaign doesn't use it — see "Feature toggles" under `config.js` below.

Everything user-facing is in **pt-BR**, hardcoded in the templates and JS. The `lang/*.json` files now contain only `TYPES.*` keys, which is all Foundry actually consumes here — the ~40 `NIHILITY.*` keys they used to carry were read by nothing (there is no `game.i18n` call anywhere in this system) and were removed so the files stop implying a translation layer that doesn't exist. Write new UI strings in pt-BR like the surrounding code; adding `NIHILITY.*` keys would not resolve anywhere.

## Commands

There is no build step and no bundler. Two local verifications exist — run both before considering a change done:

```bash
node --check module/path/to/file.js   # syntax of a single file
node --test test/rules.test.mjs       # unit tests of the pure rule functions
```

`test/rules.test.mjs` covers only what is callable without Foundry (dice pool, resistance curve, module presets, currency conversion, fusion snapshot), with `test/setup.mjs` stubbing the handful of Foundry globals the import path touches (`Math.clamp`, `foundry.utils.*`). **The bar for adding a test there is that the function needs no Actor/Item/canvas** — if a test would need to fake a Document, extract the pure part instead of growing the stub. Everything involving documents, sheets or canvas is still manual load-testing inside a running world.

**Audit trail:** `ANALISE-SISTEMA.md` at the repo root is the full audit this system was measured against (inventory, bugs with file:line, deprecation sweep, modularity roadmap). Items 1–10 of its roadmap have been executed; it is kept as the record of *why* those changes were made.

**Version bump convention (always follow this):** `system.json`'s `"version"` must be bumped in its own `chore: bump version to x.y.z` commit after every meaningful feature/fix push. Foundry's update-check compares this field against the manifest URL, so without a bump, worlds never see new content as available. Look at recent `git log` for the exact pattern already in use.

**Install for manual testing:** copy `system.json`, `module/`, `templates/`, `styles/`, `lang/` into `Data/systems/nihility-rpg-system/` in a Foundry install, or point Foundry's "Install System" at the manifest URL in `system.json` (`manifest`/`download` point at this repo's `main` branch on GitHub).

## Architecture

### Entry point and registration

`module/nihility-rpg-system.js` is the only `esmodules` entry in `system.json`. On the `init` hook it:
- Registers all Game Settings (`registerSystemSettings()` in `config.js`) and five visual Settings Menu apps (System Modules/feature toggles, Currencies, Species Presets, Damage Elements, Status Conditions — see below).
- Registers `TypeDataModel` classes onto `CONFIG.Actor.dataModels` / `CONFIG.Item.dataModels` (this system uses `documentTypes` in `system.json`, not a `template.json`).
- Unregisters the core sheets and registers this system's custom `ActorSheetV2`/`ItemSheetV2` subclasses as default (see "Sheets and Apps" below — everything UI-related runs on ApplicationV2 now, not the classic AppV1 API).
- Exposes a public API at `game.nihility` (`config`, `ai` = the `AIHelper` export from `ai-helper.js` — itself just an assembly point over several focused modules, see "AI integration and the ai-helper.js split" below, `openAssistant()` — opens `NihilityMenuApp`, the system's single GM entry point, not a bare AI assistant popup).

Other hooks worth knowing about, all in this same file: `preCreateActor` seeds a new `character` with the starting Normal Skill Points (skipped when the creation data already carries a value, so duplicating/importing an Actor doesn't gift extra points); `preUpdateActor` grants Normal Skill Points on level-up (merged into the same write, so it works even when the level changes some other way than the GM's Level Up button) and always calls `announceLevelUp` first — before the skill-point early-return, so the announcement still fires even if the per-level grant setting is 0; `preDeleteItem` cleans up Skills that an Item/Module granted when that source is deleted; `preCreateItem`/`preUpdateItem` enforce the three Módulo install rules (see "Sistema de Naves"); `renderChatMessageHTML` wires the Skill-request approve/reject buttons **and** the ship-repair buttons, and hides PAD message/contact-share cards from the normal chat log (the PAD reads `game.messages` directly, so hiding the DOM card costs it nothing); `renderActorDirectory` injects a button that opens `NihilityMenuApp` — visible to **every** user now, not just the GM, because the menu has a player-accessible "Fichas" tab (with a `game.nihility.openAssistant()` macro fallback since the injection point can vary across Foundry versions); `updateCombat` fires three ticks for whichever Actor's turn just started, all GM-only: periodic Skill effects (`tickCombatRoundEffects`), Active-Skill upkeep drain (`tickActorUpkeepSkills`), and — for Nave/Veículo only — module overload/cooldown/shield regen (`tickStarshipPower`).

**Every `game.settings.register`/`registerMenu` call must sit inside the `init` hook.** The `nihilityMainMenu` menu used to be registered at module-evaluation time, at the bottom of the file, outside any hook — unsupported by the API and one boot-order change away from breaking the whole system load. It now lives with the other five `registerMenu` calls inside `init`; keep it that way.

One-time migrations (`migrateCommonTierToNormal`, `migrateElementalDamageToMagicTag`, also in this file) run through `runMigrationIfNeeded(key, fn)`, which checks/records completion in the `completedMigrations` world setting (`getCompletedMigrations()`/`markMigrationCompleted()` in `config.js`) — **always use this wrapper for a new one-time migration**, never call a migration function directly from the `ready` hook. Without the guard a migration re-scans every Actor and the whole relevant Compendium on every single world load, forever, even decades after it already succeeded once.

### `config.js` — the single source of truth for constants and settings

`MEU_SISTEMA` is one large exported config object (tiers, attribute keys/labels, effect targets, default currencies/species/damage-elements/status-conditions, etc.) plus `SYSTEM_ID`. Every GM-configurable *flat list* (id/label/+1-2 more fields per row) follows the same pattern: a `MEU_SISTEMA.DEFAULT_X` constant, a `getActiveX()` reader that does `setting-JSON > default`, a hidden `config: false` setting storing the JSON string, and an ApplicationV2 app built by `createListConfigApp({...})` in `module/apps/list-config-app-factory.js`. This covers currencies (`currency-config.js`), damage elements (`damage-elements-config.js`), and status conditions (`status-conditions-config.js`) — each of those files is now just a `fields`/`getActiveList`/`hint` config object passed to the factory, not a hand-written `ApplicationV2` class; **extend it the same way (add a `createListConfigApp` call) for any new flat GM-editable list.** Species presets (`species-config.js`) are the one exception — nested structure (body parts + racial skills per species) doesn't fit the factory's flat-row model, so it stays a hand-written app.

`getResistanceTargetOptions()` (also in `config.js`) is the single source for the "Geral + each active damage element" dropdown shared by the Skill editor (`skill-editor-dialog.js`) and the Title sheet (`item-sheet.js`) — don't rebuild that list inline in a third place. `sceneActorCandidates({types, excludeActorId, permission})` is likewise the single source for every "pick an Actor" dropdown in the system (skill target, currency transfer, repair engineer, PAD contact share) — it deliberately lists only Actors with a Token on the **currently open scene**, never the whole Actor Directory.

**Feature toggles (modularity) — `MEU_SISTEMA.FEATURES`.** The system is built to be reconfigured per campaign (medieval fantasy / sci-fi / mixed), and every switchable block lives in **one table**: `MEU_SISTEMA.FEATURES` in `config.js`, keyed by feature id, each entry carrying `setting` (storage key), `name`/`hint`, `default`, and optionally `parent` (a sub-feature is off whenever its parent is off).

Three things read that one table and nothing else, so **adding a block is a single new line there**:
- `registerSystemSettings()` registers one `config: false` world setting per entry in a loop.
- `FeatureConfigApp` (`apps/feature-config.js` + `templates/apps/feature-config.hbs`) renders the editor, nesting sub-features under their parent.
- `MEU_SISTEMA.CAMPAIGN_PRESETS` (Fantasia Medieval / Sci-Fi Arcano / Misto) maps feature id → boolean, applied in one shot by `applyCampaignPreset()`.

**Always read a toggle through `isFeatureEnabled(key)`**, never `game.settings.get` directly — only that helper walks the `parent` chain and falls back to the table's `default` when settings aren't registered yet (which really happens when a Data Model prepares early in the boot). The named shortcuts (`isEconomyEnabled`, `isVesselsEnabled`, `isSkillFusionEnabled`, …) all delegate to it; they exist because half the codebase already imported them.

**The rule that must never break: turning a feature off only hides UI and blocks creating *new* content of that kind — it never deletes, migrates or rewrites saved data.** Turning it back on has to return the world exactly as it was. That is what makes it safe to flip presets mid-campaign. Concretely: `vessels: false` blocks `preCreateActor` for starship/vehicle and hides the AI generation cards, but existing ships still open and work; `resistances: false` removes the Resistance section from the skill editor, and a Skill that already had `resistanceTarget` keeps it untouched.

There are **two** energy labels, not one: `getCharacterEnergyLabel()` (setting key `energyLabel`, default "Mana") for Personagem/Criatura and `getStarshipEnergyLabel()` (`starshipEnergyLabel`, default "Sistema Eletro-Plasmático (EPS)") for Nave/Veículo. Never hardcode "Mana"/"EPS" in a message — use `getEnergyLabelForActor(actor)`, which picks the right one by Actor type. (`templates/starship-sheet.hbs` still hardcodes "EPS" in six places; that's a known gap, not the pattern to copy.)

Render/action logs across every Sheet/App go through `debugLog()` (`config.js`), gated by the client-scoped `debugMode` setting (off by default) — use it instead of a bare `console.log` for anything that fires on every render/click; rare lifecycle events (system init, Compendium auto-created, migration completed) stay as plain `console.log`, no gate, since those are rare enough to always want visible.

`game.settings` scope matters here: AI provider/endpoint/model/API key (and `debugMode`) are registered `scope: "client"` deliberately (not `"world"`) — a `world`-scoped setting syncs to every connected client including players, which would leak the API key. Since only the GM uses the AI Assistant, client-scope solves this without any relay infrastructure, at the cost of needing to reconfigure per-browser.

### Data Models (`module/data/`)

- `character-model.js` — `CharacterDataModel` only. Player characters, NPCs, creatures and mounts are **all** `type: "character"`, separated by `isPlayerCharacter`; there is no second Actor Data Model (there was one, `CreatureDataModel`, never registered anywhere — it was removed rather than kept in sync for nothing).
- `starship-model.js` — `StarshipDataModel` and `VehicleDataModel`, both extending the shared `ShipSystemsDataModel` base (Porte/Módulos/Grid de Energia/cascata de dano/Tripulação — see "Sistema de Naves" below). Vehicle additionally has `fuel` plus `parts`/`speed` **getters** (`speed` is derived from the Motor Módulo, not a stored field); Starship additionally has `crew` (a plain capacity number, not the `crewMembers` roster) and a `maneuverability` getter, also derived from the Motor Módulo.
- `item-models.js` — `SkillDataModel`, `BodyPartDataModel`, `TitleDataModel`, `StarshipModuleDataModel`, `GenericItemDataModel`. Several small schema-builder functions (`grantedSkillSchema()`, `statModifiersSchema()`, `attributeBonusesSchema()`, `effectEntrySchema()`) are reused across multiple of these — read them before adding a new field so you reuse rather than duplicate. `TitleDataModel.resistances` (`[{target, amount}]`) is the Title-side half of the damage-resistance mechanic — see "Resistência/Imunidade" below. `effectEntrySchema()` is the shape of one entry in a Skill/Sub-Skill's `effects[]` array (`target`, `amount`, `durationRounds`, plus `conditionId`/`periodic`/`tickUnit`/`damageElements` — see "Status Conditions and periodic ticks" below).

**The `prepareDerivedData()` pipeline in `character-model.js` encodes the game's core balance rule and must run in this order:** `deriveCombatAttributes()` before `deriveVitalStats()` (the latter reads `combat.<attr>.total`, computed by the former). The rule itself, arrived at through several rounds of explicit correction, is a strict three-tier split per combat attribute:

- `attr.total = points + Title bonus` — the only permanent base, and the **only** thing that feeds the HP/Mana Max formula. The formula shape is fixed (`Atributo A.Total × Atributo B.Total × multiplicador`, with a floor) but **which** attributes, the multiplier and the floor are GM settings read through `getVitalFormula()` — defaults reproduce the historical `Força × Defesa × 10` / `Magia × Defesa Mágica × 10`, floor 50. Setting `energyPoolEnabled: false` (a campaign with no magic) zeroes `energy.max`/`value` outright and makes `useSkillEffect` charge no cost and `tickActorUpkeepSkills` drain nothing for Personagem/Criatura — the Skill still works, the resource simply stops existing. Ships are unaffected by that flag: their Grid is a separate system.
- `attr.effectiveTotal = total + buffDelta` (buffDelta = temporary Active Effects created by a Skill's `"temporary"` effect) → `attr.bonus = floor(effectiveTotal / 3)` → feeds the escalating dice pool in `dice.js` (+1d20 per +10 of bonus, all dice summed). Temporary buffs/debuffs affect rolls but never HP/Mana.
- `attr.itemBonus` (sum of `attributeBonuses` from equipped Items / installed Body Part mods) is computed but deliberately **excluded** from both `total` and `effectiveTotal` — it never touches HP/Mana and never escalates the dice pool. It's only ever added as a flat `extraFlat` number at roll time (`rollAttribute(actor, key, { extraFlat })` in `dice.js`), matching this system's pre-existing rule that weapon/equipment bonuses "somam por fora, na hora da rolagem."

Separately, permanent `statModifiers.{hp,energy}` (present on Skill, equipped Item, and installed Body Part mods) and the `hp`/`energy` `buffDelta` stack on top of the floored formula result with no ceiling/floor of their own. `Shield` (`attributes.shield.value`) is a flat, max-less resource spent by hand as it absorbs damage — conceptually and mechanically distinct from starship shields (`StarshipDataModel.shields`).

**Attribute Point pool** (same `deriveCombatAttributes()` pass): the GM grants a budget via two settings — `attributePointsStarting` (default 35) and `attributePointsPerLevel` (default 5) — and `dataModel.attributePointsPool = {total, spent, remaining}` is derived from them each prep. Allocation is two-phase on purpose: the +/- buttons on the sheet write to `attr.pendingPoints` (never counted in `total`/`bonus`/HP/Mana, only shown as `attr.previewBonus`), and only "Confirmar" (`confirmAttributePoints` in `actor-sheet.js`) moves them into `attr.points` in a single update. "Resetar" zeroes `pendingPoints` and never touches confirmed `points`. The + button is disabled once `remaining` hits 0. Note this makes `prepareDerivedData()` read `game.settings` — unlike the other config readers it is not wrapped in try/catch, so it assumes settings are already registered.

### Skill mechanics: creation vs. runtime use

These are two separate files with two separate concerns — don't conflate them:
- `skill-economy.js` handles Skill **creation/lifecycle**: fusion (`fuseSkills`, tier-consumption rule via `canConsumeTier` — a skill can only consume sources of its own tier or lower), the Skill Point economy (break/merge/request/approve/reject, gated behind GM chat-message approval buttons), Item/Module-granted skills (`createGrantedSkill`/`removeGrantedSkill`, marked `isItemGranted: true` so they can never be fused and vanish automatically when their source is removed). Skill/Compendium creation itself is delegated to `compendium.js` (`ensureSystemCompendiums`/`registerItemInCompendium`/`getCompendiumForItemType`); the Sub-Skill-snapshot logic shared by manual fusion and AI-generated Skills lives in `skill-snapshot.js` (`buildSubSkillsFromSources`), kept separate specifically to avoid a circular import between `skill-economy.js` and `ai-generation.js` (see "AI integration and the ai-helper.js split" below — this used to be one 1166-line `ai-helper.js` file before the module was split apart).
- `skill-effects.js` handles **using** an already-created Skill (`useSkillEffect`): `effectType: "damage"` rolls the skill's free-form `damageFormula` (any Foundry dice syntax) and posts publicly, tagged with 0+ `damageElements` (flavor only); `effectType: "temporary"` applies each entry in `effects` as either a duration-bound `ActiveEffect` (targeting the `buffDelta` schema paths — this is how temporary buffs/debuffs/drawbacks are implemented), a direct Shield add (no duration), or a **periodic** tick (see immediately below).

**Fusão vs. Evolução** are two different lifecycle operations, both in `skill-economy.js`: `fuseSkills` consumes 2+ Skills into one whose `subSkills[]` are frozen mechanical snapshots of the consumed sources (always flattened — fusing a fusion inlines *its* components, never nests); `evolveSkill` is 1-to-1 — the old Skill leaves no component behind, only an `evolvedFrom` string. Both preserve the originals in the Compendium before removing them from the Actor. Both are reachable from the Actor sheet and, for Evolução, also from the Item sheet.

**Sub-Skills are usable at runtime, not just history.** `subSkillSchema()` carries the full mechanical field set of a real Skill (tier/level/cost/upkeep/animation/resistance/effectType/damageFormula/effects/targetType/area). When a Skill has Sub-Skills, "Usar Habilidade" first prompts which component to fire (`_promptSubSkillChoice` in `actor-sheet.js`), and `useSkillEffect(..., {subSkillIndex})` then resolves that component's own mechanics instead of the parent's — modelled on Tensura's umbrella Unique Skills. Each Sub-Skill also toggles its own `active` state independently (`activeStatePath(subSkillIndex)`), so one fused Skill can have several Active components running at once.

**Emissão (area targeting)** — `targetType` on a Skill (and on each Sub-Skill) is `"targeted"` (the default: pick one Actor from a dropdown) or `"emission"`, which instead has the user place a shape on the canvas and affects everyone inside it. All the canvas/geometry work lives in `module/area-effects.js` and **nowhere else** — `skill-effects.js` and the sheets only ever receive an already-resolved `Actor[]`. It is built on Foundry's Measured Templates (`CONFIG.MeasuredTemplate`), client-side only (the template is never saved to the Scene and disappears on confirm/cancel); an earlier attempt used the V14 Scene Regions API, which doesn't exist in V12/13 — don't go back to that. Shapes are `circle`/`cone`/`ray` (`areaShape`), sized by `areaDistance` and, for cones, `areaAngle`; mouse wheel rotates cone/ray, left-click confirms, right-click/Esc cancels. `areaEffectsSupported()` is the guard the sheets check before offering it. On the effect side, area versions roll the damage **once** and apply each target's own reductions to that same total (`rollSkillDamageArea`/`applySkillEffectsArea`), reporting everything in one consolidated chat message.

`isMagicDamage` (boolean) is independent of `damageElements` (array) — a skill can be magical with no element (pure arcane force), elemental with no magic tag (e.g. a flaming sword dealing physical damage), or both. Only `isMagicDamage` gates the Defesa Mágica reduction below; elements are pure chat flavor.

**Magic damage reduction**: when a damage Skill has `isMagicDamage: true` and is used against a target, `rollSkillDamage` reduces the roll by `clamp(target.system.attributes.combat.magicalDefense.total × MEU_SISTEMA.MAGIC_DEFENSE_REDUCTION_PER_POINT, 0, MEU_SISTEMA.MAGIC_DEFENSE_REDUCTION_CAP)` — a percentage (not a flat number), so it stays relevant at every level range the same way the HP/Mana formula's multiplicative scaling does. Tune the two constants in `config.js`, not the formula shape, if this needs rebalancing. Target selection is now prompted for **any** `"damage"` skill (not just magic ones, unlike before Resistance existed) — even a purely physical hit needs a target so the Resistência mechanic below has someone to check.

**Resistência/Imunidade** (`module/skill-effects.js`): a Skill can be a passive damage-reducer instead of (or as well as) anything else, via `system.resistanceTarget` — `""` (not a resistance skill), `"general"` (reduces *any* damage), or a damage-element id (reduces only that element/type — `"physical"` covers cuts/blunt trauma, already one of the default damage elements). Progression is fixed at 10%/`level`, but the ceiling differs by target: **General caps at level 5 (50%) and never becomes "Imunidade Geral"** (full immunity to everything would be too strong) — only an Elemental resistance reaches level 10/100% and auto-renames itself from `"Resistência: {Elemento}"` to `"Imunidade: {Elemento}"` (`computeResistanceName`/`computeResistancePercent`/`resistanceMaxLevel`, all exported from `skill-effects.js`). The rename only happens at two triggers — picking a Category in the item sheet, and clicking Level Up — never from an arbitrary edit of the level field, so a custom name isn't silently clobbered. Titles can *also* grant Resistance (`TitleDataModel.resistances`, a flat GM-typed percentage with no level formula, since Titles don't have levels) — for the same target, Skill and Title resistance **add together**; duplicate sources of the same kind (two Skills, or two Titles, for the same target) only count the best one, not the sum. `applyDamageReductions` applies Defesa Mágica → Resistência Geral → Resistência Elemental in sequence, each multiplying what's left of the roll.

Both damage paths report the **final** (already reduced) number in chat, never how much was reduced nor that a reduction happened at all: single-target appends `— {Alvo}: {n}` to the roll flavor, area lists one `{Alvo}: {n}` row per target. The raw roll is still visible because `roll.toMessage()` shows it — that is intentional (the dice are public, the target's defenses are not). Keep the two paths reporting the same way; they silently disagreed once and Resistência ended up meaningless against single targets for a long time.

**Status Conditions and periodic ticks** (`module/skill-effects.js`, schema in `effectEntrySchema()`): an entry in a `"temporary"` Skill's `effects[]` can carry an optional `conditionId` (id from `getActiveStatusConditions()`/`config.js`'s GM-editable catalog — Cegueira, Veneno, Atordoamento, etc., each just a label + icon; picking one gives the created `ActiveEffect` a Foundry `statuses` entry so it shows the token overlay icon, but **nothing about a Condition blocks an action by itself** — the GM adjudicates what "cego"/"atordoado" prevents at the table, same as the rest of this system's philosophy of computing numbers, not enforcing turn economy). Separately, `periodic: true` (only meaningful for `target: "hp"` or `"energy"`) turns the entry into a damage/heal-over-time tick instead of a one-shot buff: `durationRounds` becomes "how many ticks remain," and `tickUnit` picks how it advances — `"combatRound"` ticks itself via the `updateCombat` hook whenever it becomes that Actor's turn (GM-only execution, guarded so multiple connected clients don't double-apply it), `"manual"` waits for a click on the "Aplicar Tick" button next to the Condição Ativa chip on the Actor sheet header (covers long-term healing/damage outside combat, e.g. "Regeneração Amorfa" ticking once per rest, without needing any game-time/calendar system).

Reapplying the exact same named Condition (same `conditionId`) onto a target that already has it **extends** the existing `ActiveEffect`'s remaining duration/ticks instead of creating a second independent effect (`findStackableEffect` in `skill-effects.js`, matched on `conditionId` + same periodic-ness) — 5 rounds of Veneno + a second hit worth 10 more rounds leaves the target Envenenado for 15, not two overlapping instances.

A damage tick (`tickAmount < 0`) is reduced by the target's Resistência Geral + Resistência Elemental (per `damageElements` chosen on that effect entry) exactly like `rollSkillDamage`'s reduction — **except it deliberately skips Defesa Mágica entirely**, even for a "magical" Veneno; this is a one-off balance call (Veneno Mágico bypasses Defesa Mágica on purpose), not a bug, so don't "fix" it back to match `rollSkillDamage`'s pipeline without checking with the GM first. A heal tick (`tickAmount > 0`) is never reduced by anything — there's no "resist your own healing" concept anywhere in this system.

**Habilidade Ativa** (`hasUpkeep`/`upkeepCost`/`active`, shared by `SkillDataModel` and `subSkillSchema()` via the `usageFields()` builder in `item-models.js`): a Skill can be a toggle instead of (or as well as) a one-shot use. `cost` (the pre-existing field) is spent once when turning it on; `upkeepCost` then drains every round while `active` stays true, via `tickActorUpkeepSkills` (`skill-effects.js`) — called from the same `updateCombat` hook as `tickCombatRoundEffects`, so both fire once per combatant's own turn, GM-only. **The one-off `cost` and the per-round `upkeepCost` are spent through two completely different mechanisms** — this split is the whole design, don't collapse it:
- **One-off `cost`** comes from a *persisted* field (`energyValuePath`/`currentEnergyValue`): `attributes.energy.value` for Personagem/Criatura, `powerGrid.capacitor.value` for Nave/Veículo. It must be persisted — this used to point at `powerGrid.reactorOutput`, which `prepareDerivedData()` recomputes from the Reator Módulo every prep, so the deduction was overwritten on the next preparation (ship skills were free) and a ship with no Reator read 0 and could never pay anything. `capacitor.max` is always derived and **never zero**: with no Bateria Módulo it falls back to `MEU_SISTEMA.CONDUIT_CAPACITOR_BY_SHIP_SIZE` — the charge already sitting in the hull's own power conduits — and installing a Bateria **replaces** that value rather than adding to it. The whole conduit table is deliberately kept below 125 (the capacity of the smallest installable Bateria, Compacto) so that replacing is never a downgrade at any Porte; `test/rules.test.mjs` locks that invariant, so raising a conduit value fails the suite instead of silently making a Bateria an upgrade that isn't one.
- **Per-round `upkeepCost`** is *not written anywhere* for ships. `ShipSystemsDataModel.activeUpkeepDrain` sums the upkeep of every Active Skill/Sub-Skill and `prepareDerivedData()` subtracts it from the Reactor's generation: `powerGrid.reactorOutput = reactorBaseOutput - activeUpkeepDrain`. The Skill's own `active` flag *is* the persistence, so switching it off returns the energy with no compensating write to get wrong. `tickActorUpkeepSkills` then only enforces the ceiling for ships (`enforceShipUpkeepCapacity`): Skills whose combined upkeep exceeds `reactorBaseOutput` get force-deactivated, in sheet order. Personagem/Criatura keeps the original behaviour (`drainCharacterUpkeep` really subtracts from the pool, one source at a time, since order matters when there isn't enough for all). Energy hitting 0 mid-upkeep force-deactivates the Skill (`warnInsufficientEnergy` whispers only the user who tried to act). Toggling a `"damage"`-type Active Skill off never re-prompts for a target (`isDeactivating` short-circuit in both `actor-sheet.js#onUseSkill` and `starship-sheet.js#onUseSkill` — deactivation is symmetric with whatever target it was originally applied to, not a new action).

Reapplying (re-toggling on) an Active Skill whose `effects[]` include a duration-bound buff or a periodic tick must never let the reapplication silently extend/refresh what's already running — the **anchor** mechanism in `applyEffectsToActor`/`tickPeriodicEffect` (`skill-effects.js`) exists specifically for this: each created `ActiveEffect`/periodic tick records which Active Skill "anchors" it, and turning the same Skill off is what actually lets it expire/removes it (`removeUpkeepLinkedEffects`) — not a fixed duration ticking down independently of the toggle state. A periodic (Veneno/cura) entry's `displayTicks` being `null` means "until deactivated," rendered as such in the Condição Ativa chip, rather than a numeric countdown.

**Animação** (`animationPath`, same `usageFields()` builder): an optional Sequencer effect path played by `playSkillAnimation()` (`module/vfx.js`) whenever `useSkillEffect` fires — `vfx.js` is a soft dependency (`sequencerAvailable()` checks `typeof Sequence !== "undefined"` and no-ops entirely if the Sequencer module isn't installed/active), fire-and-forget (never awaited by the calling effect logic, so a slow/missing animation never blocks the actual mechanical resolution).

Racial-tier skills only ever come from a Species preset (never bought with Skill Points); Ultimate-tier only ever comes from fusion (never bought directly) and is hidden from players in tier dropdowns/lists until they own one — but always visible to the GM (every tier-visibility filter in the sheets is `tier !== "ultimate" || game.user.isGM` or equivalent, deliberately).

**Level Up is GM-only**: the Nível field is `readonly` for non-GM on both the Actor sheet (`system.attributes.level`) and the Skill item sheet (`system.level`) — the only way either goes up is the GM-only "+" button next to each (`levelUpActor` in `actor-sheet.js`, `levelUpSkill` in `item-sheet.js`). Both announce via "Voz do Mundo" (actor level-up reuses the pre-existing `announceLevelUp`; skill level-up is a new `kind: "skill-level-up"` call). `levelUpSkill` also refuses to increment past a Resistance skill's `resistanceMaxLevel` (5 or 10) instead of over-leveling it silently.

### Sistema de Naves (Overhaul de Porte/Módulos/Energia)

Nave Espacial (`type: "starship"`) e Veículo Terrestre (`type: "vehicle"`) both extend `ShipSystemsDataModel` (`module/data/starship-model.js`) — a shared base with Porte, Módulos, Grid de Energia, cascata de dano e bônus de combate, so the two types are mechanically identical except Vehicle is locked to the two smallest Portes and additionally has `speed`/`fuel`/`parts` (plain `type: "item"` gear, distinct from `starship_module`). Porte (`shipSize`, `MEU_SISTEMA.SHIP_SIZES`/`VEHICLE_SIZES`) is GM-only editable in the header (`{{#unless isGM}}disabled{{/unless}}` on the `<select>`, same pattern as Nível).

**Módulos** (`StarshipModuleDataModel`, `item-models.js`) are `type: "starship_module"` Items with a `category` (`MEU_SISTEMA.STARSHIP_MODULE_CATEGORIES`) and a `moduleSize` (Compacto→Colossal, `MEU_SISTEMA.MODULE_SIZES`) that reuses the exact same scale for Arma's own Porte. Seven categories are **slot único** (`MEU_SISTEMA.STARSHIP_SINGLE_SLOT_CATEGORIES` — Reator/Bateria/Distribuidor/Escudo/Motor/Casco/FTL): only one Módulo of that category can exist per Actor, enforced by a `preCreateItem`/`preUpdateItem` hook pair in `nihility-rpg-system.js` (`checkSingleSlotAvailable`) that also checks Porte compatibility (`checkModuleSizeCompatibility` — a Módulo's `MODULE_SIZE_RANK` can't exceed the ship's `SHIP_SIZE_RANK`) and Arma's space budget (`checkWeaponBudget` — Arma is NOT slot-único, instead every installed weapon consumes `MODULE_SIZE_RANK + 1` units against `weaponSlotBudget`, a getter on `ShipSystemsDataModel` that reads `MEU_SISTEMA.WEAPON_SLOT_BUDGET_BY_SHIP_SIZE`). `ShipSystemsDataModel.singleSlotModule(category)`/`reactorModule`/`shieldModule`/etc. are the getters everything else reads instead of tracking an id by hand.

**Presets and auto-fill**: `MEU_SISTEMA.MODULE_SIZE_PRESETS[category][moduleSize]` + `MODULE_HP_BY_SIZE[moduleSize]` (config.js) are suggested stats, not enforced values — `getModuleSizePreset(category, moduleSize)` (config.js) returns them pre-flattened as `"system.field": value` pairs ready for `.update()`/`createEmbeddedDocuments()`. Three call sites share this one source of truth: `NihilityItemSheet#_onModulePresetChange` (item-sheet.js) re-suggests stats when the GM changes Categoria/Porte in the editor — but only overwrites a field still at its schema default, never a hand-edited value (`fieldDefaults` map handles the few fields whose default isn't `0`/`""`, e.g. `transferFactor`/`warpFactor` default to `1`, `hp.value`/`hp.max` default to `20`); `TabbedActorSheetV2.onItemCreate` (starship-sheet.js) seeds a freshly-created Módulo with its Standard-tier preset immediately; `generateVesselFromAI` (ai-generation.js) does the same for AI-generated ships — the AI only ever picks category/moduleSize/name/description, never invents a stat number. Every capacity-like preset field scales by `MEU_SISTEMA.MODULE_SIZE_MULTIPLIER` (×1/2/4/8/16 per Porte, chosen specifically so a Porte bump also doubles that Módulo's power draw — the Grid strain this creates is what discourages casual swap-to-bigger-Módulo, not a currency cost); percent-capped and time-based fields (Penetração/Redução/Recarga/Carga) intentionally do **not** follow that curve (a doubling Recarga every tier would make big weapons unusable) and are hand-tuned per tier instead.

**Energia** (Elite Dangerous-inspired Reator→Distribuidor→Bateria chain): every Módulo has `powerAllocationPercent` (throttle, no ceiling) and `powerPriority`. `ShipSystemsDataModel.totalConsumption` sums `powerConsumption × powerAllocationPercent/100` across online Módulos; `transferCapacity` is the Distribuidor's teto for the whole ship (`baseline(Porte) × distributorModule.system.transferFactor`, from `MEU_SISTEMA.DISTRIBUTOR_BASELINE_BY_SHIP_SIZE`); `powerShortfall` is a **never-persisted** getter, memoized for one data-prep cycle (`#shortfallCache`), that — only when `totalConsumption` exceeds `min(reactorOutput, transferCapacity) + capacitor.value` — funds online Módulos in `powerPriority` order (lowest first) and returns the fraction each one actually gets this instant (`powerRatioFor(module)`). `prepareDerivedData` runs in two explicit phases because of that cache: **Fase A** settles the shortfall's *inputs* (Reator output, Capacitor max, and the Capacitor value clamp), **Fase B** then reads a stable shortfall for everything derived from it (Escudo, Motor…). The cache is invalidated at the start of the prep and again between the two phases — keep that second invalidation if you touch this, or Fase B freezes on a half-built Fase A state. `effectiveModuleStat(module, field)` (the one helper basically everything derived reads) multiplies a Módulo's base stat by both its own throttle ratio AND this starvation ratio — this is how Reator's `reactorOutput`, Escudo's `shieldCapacity`/`shieldRegen`, Motor's `acceleration`/`rotation` (→ `StarshipDataModel.maneuverability`/`VehicleDataModel.speed`, no longer free-typed fields, purely derived), and Bateria's `batteryCapacity` (→ `powerGrid.capacitor.max`) all end up scaled — running short on power isn't a UI warning only, it's mechanically real the instant you read any of these. Reator/Distribuidor/Bateria don't get a throttle control in the item editor UI (their fields aren't meaningfully "overclockable" the same way); Reator instead reuses the same `powerAllocationPercent` field as its Under/Overclock — Underclock (<100%) never damages, any Overclock (>100%) does, no tolerance band, unlike every other category's threshold (`MEU_SISTEMA.OVERLOAD_THRESHOLD_REACTOR`/`_SHIELD`/`_DEFAULT`).

**Sobrecarga** (`tickStarshipModuleOverload`-equivalent logic in `module/starship-power.js`'s `tickStarshipPower`, called from the same `updateCombat` hook as the Skill ticks): a Módulo whose `powerAllocationPercent` exceeds its category's threshold takes `(excess/100) × hp.max × MEU_SISTEMA.OVERLOAD_DAMAGE_PERCENT_OF_MAX_PER_ROUND` per round (`0.5`, tuned to ~5% of max HP per round per 10 points of excess). Any Módulo whose `hp.value` hits 0 force-offlines itself regardless of cause (overload here, combat damage, manual GM edit) and can't be manually re-toggled online below `MEU_SISTEMA.MODULE_RESTART_HP_THRESHOLD_PERCENT` (15%) of `hp.max` — checked both in this tick and in `TabbedActorSheetV2.onToggleModulePower` (`moduleCanRestart()` from `starship-power.js`). Arma is exempt from this whole mechanic (see below) and so are Bateria/Distribuidor (no throttle to overclock in the first place). The same tick also decrements Arma's `cooldownRemaining` and FTL "Salto"'s `chargeRemaining`, runs `applyPowerGridTick()` last so the Capacitor actually charges/discharges during combat (it used to move only when someone clicked the manual button on the sheet — which stopped being acceptable once the Capacitor became the pool that pays Skill costs), and handles Escudo's Regen/Recarga (`computeShieldTickPatch`): `rechargeRemaining > 0` blocks regen entirely (0% protection during Recarga), set by the damage cascade the instant `shields.value` hits 0; once it reaches 0 the Escudo resumes regenerating `shieldRegen`/round toward `shields.max`.

**Cascata de dano** (Escudo → Casco → Integridade Estrutural, `applyStarshipDamageCascade` in `skill-effects.js` — the one part of ship damage that applies automatically via `targetActor.update()`, unlike Personagem/Criatura damage which stays a chat number the GM applies by hand on purpose): a hit is split by the attacking Arma's Penetração (`shipWeaponPenetration(sourceActor, weaponModule)` — `effectiveModuleStat(weaponModule, "penetration")` as the base, `combatBonuses.weaponPenetrationFlat/Multiplier` stacking on top from aprimoramento Skills) at each of the first two stages: the non-penetrated portion tries to be absorbed by that layer's current pool (capped at what's left, overflow leaks forward), the penetrated portion always leaks forward regardless. Casco's own `armorReductionPercent` (from the `armor` Módulo, `hp.max` feeding `casco.max`) reduces the leaked amount **before** its own Penetração split — but only while `casco.value > 0`: a Casco already worn through (0 HP) stops reducing anything, full damage reaches whatever's left of that hit. `hull` (labeled "Integridade Estrutural" in the UI — the definitive name, not "Estrutura") is the final layer, no reduction of its own. `rollSkillDamage`/`rollSkillDamageArea` branch to this cascade for any `isShipLike(targetActor)` (Nave or Veículo) instead of the Personagem `applyDamageReductions` path.

**Armas** are native to the Módulo now (Fase 5 of the overhaul), not only a Skill a Módulo grants: `damageFormula`/`penetration`/`cooldownRounds`/`cooldownRemaining` live directly on a `category:"weapon"` Módulo, fired via the `fireWeapon` action → `fireStarshipWeapon()` (`skill-effects.js`), which rolls the formula, scales it by throttle+power-starvation (same `effectiveModuleStat`-style math) and `combatBonuses`, then runs the same damage cascade using that specific weapon's Penetração. Arma's own overload rule diverges from every other category on purpose: throttle above 100% never damages the Módulo — it scales Dano/Penetração up **and** scales `cooldownRounds` by the same ratio (rounded up, minimum 1), so overclocking a weapon hits harder but reloads slower, rather than risking destroying it. `grantsSkill` still works independently for non-damage abilities a Módulo wants to grant (Casco/Utilidade modules commonly use this) — it was never replaced, just no longer the only way an Arma deals damage. FTL (`category:"ftl"`) has two mutually-exclusive sub-types sharing the one slot (`ftlType: "warp"|"jump"`): Dobra (`"warp"`, the default) is continuous propulsion with no cooldown (`warpFactor`, subject to the normal throttle curve); Salto (`"jump"`, meant to be rare/narratively gated by the GM, not mechanically restricted) uses `jumpRange` + `chargeTime`/`chargeRemaining` (same cooldown-countdown pattern as Arma).

**Ajuste manual do Mestre**: the character sheet's `.vital-adjust-popover` pattern (a toggle button opening a small +/- input) was generalized in `starship-sheet.js` into `toggleModuleVitalAdjust`/`adjustModuleVital`, driven entirely by `data-scope` ("actor"|"item")/`data-item-id`/`data-field`/`data-max-field` on each button instead of a hardcoded `vital` name — the same two actions cover Escudo/Casco/Integridade Estrutural pools on the Actor, `hp` on any individual Módulo, Escudo's `rechargeRemaining`, and Arma's `cooldownRemaining`, all GM-only (`{{#if isGM}}`). Each `<li>` wraps its visible row in an inner `<div class="item-row">` (not the `<li>` itself) specifically so the popover can be a second block-level sibling inside the same `<li>` without becoming an invalid direct `<ol>` child — don't move `.item-row`/`data-item-id` back onto the `<li>` when touching this template, the `.closest(".item-row")` lookups in every row action depend on it staying on the inner `div`.

**Tripulação** (`crewMembers` in `shipSystemsSchema()`, `crewActors` getter): a list of `{actorUuid, role}` on the Nave/Veículo — the Personagem documents stay independent, only the *association* lives here. `crewActors` resolves them with `fromUuidSync` (a Data Model getter can't be async) and silently drops entries whose Actor was deleted without rewriting the stored list — reading must never mutate. GM-only to edit, via drag&drop onto the "Tripulação" tab of the ship sheet (`_onDropCrewMember`/`onRemoveCrew`/`_onChangeCrewRole` in `starship-sheet.js`). Every crew change must also call `syncLibraryOwnershipToCrew()` (`pad/pad-library.js`) so someone who leaves the crew loses access to the ship's PAD Library. The inverse lookup ("which ships does this Personagem crew?") can't be a Data Model getter at all — it's a cross-Actor scan, so it lives in `pad/pad-crew.js` as `findCrewedShipsForActor()`.

**Bônus de Nave vindos de Skills**: `MEU_SISTEMA.EFFECT_TARGETS` includes two ship-only targets, `shipWeaponDamage` and `shipWeaponPenetration` (listed in `SHIP_EFFECT_TARGETS`). They don't map to a `buffDelta` path like the other targets do — each stores Flat and Multiplier in *separate* fields under `system.combatBonuses`, so `resolveEffectTargetPath(entry)` picks the field by the entry's `modifierType` (`"flat"` → `ACTIVE_EFFECT_MODES.ADD`; `"multiplier"` → `MULTIPLY`, where `amount` is read as a percentage, so 20 becomes the factor 1.20 — that's why `weaponDamageMultiplier` initialises to 1 and not 0). `applyShipWeaponBonus`/`shipWeaponPenetration` apply Multiplier first, then Flat.

**Reparo** (`module/starship-repair.js`, exposed as `game.nihility.requestShipRepair()` — one of the system's public macro APIs alongside `openAssistant()`): a player picks a Nave/Veículo they can Observe, a target (any Módulo's `hp`, or the Actor's Escudo/Casco/Integridade Estrutural pool), and an engenheiro Personagem they own; this whispers a chat card to the GM with a free modifier field. "Rolar Destreza" (GM-only) rolls `rollAttribute(engineer, "dexterity", {extraFlat: modifier})` — same escalating-dice formula as any other attribute roll — and the GM judges success by eye, same philosophy as the rest of the system (no DC baked in). "Restaurar Vida" (GM-only, appears after the roll) then rolls `MEU_SISTEMA.REPAIR_ROLL_FORMULA` (`"2d6"`) and applies it clamped to the target's max — the same flat formula regardless of target size, so a bigger Módulo just needs more successful attempts rather than a size-scaled roll.

### PAD — the in-game phone (`module/apps/nihility-pad.js` + `module/pad/`)

A smartphone-style app bound to one Personagem, opened from a button on that Actor's sheet. The button shows for the GM always (it's a GM tool, not physical possession) and for a player only when the Actor owns at least one `type: "item"` Item flagged `isPadDevice: true` — `hasPadDevice()` in `pad-crew.js`; being *equipped* is deliberately not required. Everything is gated by `padEnabled` plus one sub-setting per screen. The app instance uses a per-Actor `id` (`nihility-pad-<actorId>`) so reopening focuses the existing window instead of two PADs fighting over the same DOM node, and the GM can switch "persona" from the Mensagens screen — reassigning `this.actor` re-points *every* screen, not just chat.

Three screens, three deliberately different storage strategies:
- **Nave** — read-only status of the Nave/Veículo whose `crewMembers` include this Actor (Casco/Escudo/Reator/Consumo/Módulos/tripulação), with a picker when the character crews more than one. No storage of its own.
- **Biblioteca** — drag&drop favourites of any document. *Pessoal* is a plain Actor flag (`padLibrary`) — the player already owns their Actor, so permissions are trivially correct. *Da Nave* is a `JournalEntry` in a hidden World Compendium (`padLibrary` pack) holding data only in `flags`, with explicit per-document `ownership` recomputed from the current crew (`syncLibraryOwnershipToCrew`). Same pattern as `world-backup.js`; `content` is never used.
- **Mensagens** — direct and group chat built entirely on native `ChatMessage` with `whisper` + structured `flags` (the same trick as Voz do Mundo), so cross-client replication is free and no custom socket is needed. Direct threads get a deterministic id from the two sorted UUIDs (`directThreadId`), so both sides compute the same thread with no lookup table. Groups need a *persisted* entity (an empty conversation can't be derived from messages that don't exist yet), so they're `JournalEntry` documents in a second hidden pack (`padGroups`), again flags-only, with `ownership` synced to the current members. **The GM is whispered into every conversation, always** — an invisible member by convention, same privacy model as Voz do Mundo. Message bodies are escaped on the way in (`escapeHtml`) and rendered with `{{ }}`, never `{{{ }}}`.

Contacts: `getContactsFor()` combines visible PCs, current crewmates (always reachable, even if normal visibility wouldn't cover them), NPCs only when the GM is driving, plus `padContacts` (an Actor flag) — saved contacts override all the other rules on purpose, which is what makes "compartilhar contato com a cena" able to introduce an NPC to a player. Sharing is opt-in on the receiving side: `shareContactWithScene` only posts an offer card, and the recipient clicks to add it.

Live updates come from `updateActor` + `createChatMessage` hooks registered in `_onRender` (guarded so repeated renders don't stack listeners) and removed in `close()`.

### AI integration and the `ai-helper.js` split

`ai-helper.js` used to be one 1166-line file owning everything from Compendium management to currency conversion to AI generation. It was split (2026-08) into focused modules, each with a single concern; `ai-helper.js` itself is now just ~60 lines that import from all of them and assemble the `AIHelper` object exposed at `game.nihility.ai` — **nothing in the rest of the codebase imports individual functions from `ai-helper.js` anymore, only `AIHelper` itself (only `nihility-rpg-system.js` does even that)**. Import the function you need directly from the module that owns it:
- `compendium.js` — `ensureSystemCompendiums`, `getCompendiumForItemType`, `registerItemInCompendium`. Used by almost everything else in this list. `MEU_SISTEMA.COMPENDIUM` declares six World packs (Skills, Partes do Corpo, Títulos, Módulos de Nave, Biblioteca do PAD, Grupos do PAD), all created on `ready`; the AI backup pack in `helpers/world-backup.js` is a seventh that creates itself outside this list. `registerItemInCompendium` decides "is this the same Item?" through `itemFingerprint` (name + tier + sorted fusion lineage), not by name alone — two different Skills called "Corte" used to collapse into one entry, and fusion (which registers its sources before consuming them) could then recover the wrong one. Entries created before the fingerprint existed are still matched by bare name, so existing worlds don't suddenly duplicate their whole Compendium.
- `skill-snapshot.js` — `buildSubSkillsFromSources` only. Split out specifically so `skill-economy.js` and `ai-generation.js` could both depend on it without depending on *each other* (see the circular-import note in "Skill mechanics" above) — if you're tempted to inline this elsewhere, don't; keep the one shared copy.
- `skill-economy.js` — Skill creation/lifecycle (fusion, evolution, granted skills, Skill Point economy) — see "Skill mechanics: creation vs. runtime use" above.
- `currency.js` — `convertActorCurrency`, `transferCurrency`. Currency conversion never leaves a fractional amount on the destination currency: `applyWholeCurrencyAmount` (private to this file) recursively cascades any fractional remainder down into the next-lower-`baseValue` currency (careful with this function if you touch it — it was fixed once for a bug where the cascade could land back on the source currency and get overwritten instead of accumulated).
- `voice-of-the-world.js` — `announceVoiceOfTheWorld`, `announceLevelUp`. "Voz do Mundo" is the system's private-announcement channel (level-ups, fusions, new skills, currency transfers) — always sent via `whisper` to GMs + the Actor's owning player(s), never public. Don't make this public without being asked; that's a deliberate design choice, not an oversight.
- `ai-generation.js` — everything that actually talks to an AI provider, routed through `generateJSON()`/`callAIProvider()` (`generateJSON` is private to this file; `callAIProvider` lives in `module/ai/providers.js`, which adapts either OpenAI-compatible Chat Completions or the native Anthropic Messages API — the only place that knows either wire format). Two distinct capabilities:
  - **Create**: `generateActorFromAI`, `generateVesselFromAI`, `generateNoteFromAI`, `generateSkillFromAI`, `generateItemFromAI`, `generateFreeform` — always create a brand-new document. `generateActorFromAI` asks the model for **attribute points**, never for HP/Mana — those are derived, so a generated `hp` would be silently overwritten (it used to be, leaving every AI NPC on zeroed attributes and the HP floor); the Actor is then topped up to full HP/Mana once. `generateVesselFromAI` deduplicates single-slot Módulo categories *before* creating them, because everything goes out in one `createEmbeddedDocuments` call and the `preCreateItem` guard can't see not-yet-created siblings.
  - **Edit in place**: `editDocumentWithAI(doc, instruction)` — sends the doc's current `{name, type, system}` snapshot plus a free-text instruction, expects back a JSON patch restricted to `name`/`img`/`system.*` keys (`sanitizeDocumentPatch` strips anything else, e.g. `_id`/ownership), and applies it via `doc.update()`. Only Actor/Item are supported (not JournalEntry). Driven from `module/apps/ai-assistant.js`'s "Editar Existente" mode, which resolves the drag-dropped target via `TextEditor.getDragEventData`.

Dependency direction is a DAG, not a cycle: `ai-generation.js` depends on `compendium.js`/`skill-snapshot.js`/`voice-of-the-world.js`; `skill-economy.js` depends on those three *plus* `ai-generation.js` (for the "auto" mode of `fuseSkills`, which asks AI to write a Skill Única/Ultimate); `ai-helper.js` sits on top of everything. If you ever need something from `skill-economy.js` inside `ai-generation.js`, that's a sign the shared piece belongs in a new low-level module (like `skill-snapshot.js`) instead, not a reason to import `skill-economy.js` there directly.

### Sheets and Apps — all ApplicationV2 now

Every sheet/app in this system was migrated off the classic AppV1 API (the same framework mismatch — `html.querySelectorAll` called on what is actually a jQuery object under AppV1 — once broke `nihility-menu.js` outright; ApplicationV2 hands you a plain `HTMLElement` instead, so that whole bug class is gone). The shared conversion pattern, if you're adding a new sheet/app or touching an existing one:
- `class X extends foundry.applications.api.HandlebarsApplicationMixin(Base)`, where `Base` is `foundry.applications.api.ApplicationV2` (plain apps: menu, AI assistant, config editors) or `foundry.applications.sheets.ActorSheetV2`/`ItemSheetV2` (Document sheets).
- `static DEFAULT_OPTIONS = {...}` (object literal, not a getter) with an `actions: { actionName: MyClass.#onActionName }` map — referencing a `static async #onX(event, target)` declared later in the same class body works fine (private static methods are attached before static field initializers run, regardless of textual order). Handlers run with `this` bound to the app instance; `target` is the element carrying the matching `data-action`.
- `static PARTS = { body: { template: "..." } }` — every part's template needs **exactly one root HTML element** (`Template part "body" must render a single HTML element` if not) — the old AppV1 templates that used to open with a bare `<form>` now need that as their single wrapping tag (or a plain `<div>`, for non-document apps that don't need `tag: "form"`).
- `getData()` → `async _prepareContext(options)` (call `super._prepareContext(options)` first and extend that object — don't return a fresh one). `activateListeners(html)` + jQuery `html.find(...)` → `data-action` attributes in the template, or for non-click events (a `change` listener, drag&drop) manually wired in `_onRender(context, options)` against `this.element.querySelector(...)` (plain DOM, not jQuery).
- Tabs: ApplicationV2 doesn't inherit AppV1's tab mixin. Every tabbed sheet/app here uses the same hand-rolled pattern instead — `this.activeTab` on the instance, a `selectTab` action reading `target.dataset.tab`, and the template driven by `{{#unless (eq activeTab "x")}}hidden{{/unless}}` rather than the old `data-group`/`data-tab` core tab classes.
- `Dialog.wait`/`Dialog.confirm` → `foundry.applications.api.DialogV2.wait`/`.confirm` — `buttons` is an array (`[{action, label, default, callback: (event, button, dialog) => value}]`), and the callback reads form fields off `dialog.element` (plain DOM) instead of a jQuery-wrapped `html`.
- Document sheets (`ItemSheetV2`/`ActorSheetV2`) keep the old `submitOnChange` behavior via `form: { submitOnChange: true, closeOnSubmit: false }` — no `form.handler` override needed, the DocumentSheetV2 default already applies the diff to the Document.

`module/sheets/*.js` + `templates/*.hbs` are the Actor/Item sheets built this way; `module/apps/*.js` + `templates/apps/*.hbs` are the rest (`NihilityMenuApp`, `AIAssistantApp`, the four config editors — three of them built by `list-config-app-factory.js`, see the `config.js` section above —, `skill-editor-dialog.js`'s `openSkillEditorDialog` — a `DialogV2`-based modal, not a full app, used for Species-preset racial skills so they get the same field set as a real Skill instead of a stripped-down inline row).

### Handlebars context depth

Templates lean on Foundry's `eq`/`lookup`/`editor` helpers and nested `{{#each}}` blocks reading from `config.*`. Handlebars `{{#if}}`/`{{#unless}}` do **not** push a new context, but `{{#each}}` does — when adding a `../config.X` or `{{lookup ../../config.Y ...}}` reference, count the actual `{{#each}}` nesting depth from that point, not the visual indentation; getting this off by one silently renders an empty dropdown.

### Agent mode: tool-calling AI assistant

`module/apps/ai-assistant.js`'s third mode ("Agente", alongside the pre-existing "Criar"/"Editar") lets the GM ask for a *mix* of content in one prompt (e.g. "crie 3 skills e 2 personagens") and have the AI ground itself in the actual system state before proposing anything:
- `module/ai/providers.js` — `callAIProviderWithTools`/`appendAssistantAndToolResults` extend the existing single-shot `callAIProvider` with multi-turn tool-calling for both wire formats (Anthropic `tool_use`/`tool_result` blocks vs. OpenAI-compatible `tool_calls`/`role:"tool"` messages) — still the only place that knows either format.
- `module/ai/agent-runner.js` — `runAgentTask` drives the loop: calls the provider, executes whichever tool the model asks for, feeds the result back, repeats until the model stops or `maxTurns` is hit. Never touches the world directly.
- `module/ai/agent-tools.js` — `createAgentTools()` returns the actual tools: read-only ones for grounding (`list_skills`, `list_actors`, `get_system_rules`) and `propose_skill`/`propose_character`/`propose_edit`, which only push an already-normalized, schema-correct document into a `proposals` array — nothing is created yet.
- The app renders `proposals` as a review checklist; only on "Aplicar selecionados" do documents actually get created/edited (via the same `registerItemInCompendium`/`Actor.create`/`sanitizeDocumentPatch` primitives the other AI paths already use).
- Every apply records one entry in `module/helpers/world-backup.js` (a hidden World Compendium of `JournalEntry`, `recordBatchOperation`/`undoBatchOperation`/`listRecentBatchOperations`) so a whole batch — not just one document — can be undone from the same app. This replaced an earlier `localStorage`-based backup helper that didn't sync between GM/players and only tracked one document at a time; don't reintroduce that pattern.

`module/apps/nihility-menu.js` is the system's single entry point — reachable from `game.nihility.openAssistant()` and the Actor Directory button — and is where every one of these modes gets opened from. It has **five** rail tabs, not four: "Fichas" (an Actor browser with search/type filter, the one tab **players** can use — it lists Actors they own or can Observe) plus `GM_ONLY_TABS` = Configurações Gerais / Assistente de IA / Geração Automática / Ferramentas de Admin. GM-only tabs render with a padlock for players rather than disappearing, and are blocked twice — in `#onSelectTab` and again in `#onRunAction`. Every button is wired to real functionality: Economia/Anatomia/Condições open `CurrencyConfigApp`/`SpeciesConfigApp`/`StatusConditionsConfigApp` directly, Títulos opens the world's Títulos compendium browser, the `generate-*` actions route through `AIAssistantApp`'s `initialTask`, `sync-data` re-runs `ensureSystemCompendiums()`, and `export-data`/`import-data` bundle the four visually-edited settings (currencies/species-presets/damage-elements/status-conditions) into a downloadable/importable JSON via Foundry's `saveDataToFile`/`readTextFromFile` — `statusConditionsData` is treated as optional on import (not part of `hasExpectedShape`) so older exports from before it existed still load without erroring. The Configurações Gerais tab leads with **Módulos do Sistema** (`FeatureConfigApp`) and also exposes Tipos de Dano (`DamageElementsConfigApp`), which used to be registered but unreachable from here. Tabs for blocks the campaign turned off are dropped from the rail entirely (not padlocked like GM-only ones) — "this campaign doesn't use that" reads differently from "you can't touch that" — and the active tab falls back to Fichas if it just disappeared. Every menu action now has a button, including `open-ai-assistant` (card "Assistente Completo", the only route from the menu into the Editar/Agente modes) and `create-macros`, which builds the `game.nihility.*` hotbar macros in the world — idempotent by macro name, and the Repair one is created with `ownership.default: OBSERVER` because requesting a repair is a *player* action.

### Foundry version compatibility — `helpers/foundry-compat.js`

`system.json` declares `minimum: 13` / `verified: 14`. V12 is **not** supported: the V13 render hooks hand you a plain `HTMLElement` where V12 handed jQuery, and the whole codebase now assumes the former (there is no jQuery anywhere in `module/`).

Every API the V13 release moved into a namespace goes through `module/helpers/foundry-compat.js`, which is the single place allowed to name them: `renderSystemTemplate`, `pickImageFile`/`filePickerClass`, `getDragEventData`/`textEditor`, `compendiumCollectionClass`, `actorsCollection`/`itemsCollection`, `coreActorSheetClass`/`coreItemSheetClass`, `saveTextToFile`/`readFileAsText`. **Never call `renderTemplate`, `FilePicker`, `TextEditor`, `CompendiumCollection`, `Actors`/`Items`, `saveDataToFile` or `readTextFromFile` directly** — those bare globals are V12-era deprecation shims that disappear in a future release, and they were all removed from this codebase on purpose. The chat hook is `renderChatMessageHTML` (not the old `renderChatMessage`), which delivers an `HTMLElement`.
