# config.js, catálogos e Data Models

> Parte do guia do projeto. O índice e as regras que valem em todo lugar estão no `CLAUDE.md` da raiz. Quando o texto diz "abaixo"/"acima" ou cita uma seção que não está aqui, procure-a pelo índice.

## `config.js` — the single source of truth for constants and settings

**Reading the rest of this file:** wherever it says something lives "in `config.js`", read *exported by* `config.js` — that is still where every caller imports from. The code itself is in `core/config/<kind>.js`: catalog readers and `getActive*` in `catalogs.js`, `is*Enabled`/`getFeatureOption` in `features.js`, pure rules in `rules.js`, XP/level/scaling curves in `progression.js`, Actor helpers in `actors.js`, `registerSystemSettings` in `settings.js`, and `NIHILITY.DEFAULT_*` data in `defaults/`.

**Catalog readers are cached (1.69.0, backlog A3)** — `core/config/cache.js` (`createRawCache`, `memoByObject`, pure/tested) and `cachedCatalog`/`cachedList` in `catalogs.js`. Every `getActive*` (currencies, damage elements, traits, scales, Conditions, body Functions, Heritages, Species, attributes) and the vessel/structure/ammo/crew/module-category catalogs keep their parsed **and normalized** result keyed by the saved setting **text**: same text → same object; the GM saves another catalog → the text changes → the next read rebuilds (no manual invalidation, no F5). `getElementAffinityMatrix` is memoized on the element list object. When the setting doesn't exist yet (early boot, tests) nothing is cached and behaviour is the old one. `getVesselSizes` caches only the JSON read (its fallback also depends on the `shipManeuver` options). **Callers must not mutate what a reader returns** — it is the same object for everyone; clone first (`foundry.utils.deepClone`), as every catalog editor already does. This was audited when the cache went in (editors copy or rebuild from the DOM; normalizers like `normalizeSpeciesCatalog` build new objects).

**Split in 1.68.0 (backlog A2), with no behaviour change.** `core/config.js` is now a 20-line entry point that only does `export * from "./config/…"`; **everything keeps importing from `core/config.js`**, never from the folder. Inside `core/config/`: `constants.js` (`SYSTEM_ID`, `NIHILITY` — the default catalogs and tables, plus the part-% post-processing loop), `catalogs.js` (the `getActive*` readers, labels, settings-backed configs), `features.js` (`isFeatureEnabled`/`getFeatureOption`, every `is*Enabled`, campaign presets, migrations record, `debugLog`), `progression.js` (XP curve, Skill level cycle, damage scaling, vital formula, point budgets), `actors.js` (`sameActor`, `actorToken`, `actorElements`, `actorTraits`… — the Actor helpers), `rules.js` (pure rules: inventory, power grid, movement, antimagic surcharge…), `settings.js` (`registerSystemSettings`). The big default **data** blocks live in `core/config/defaults/` — `species.js` (Species, Heritages, body Functions, Traits, carry), `elements.js` (damage elements fantasy/sci-fi, `PHYSICAL_SUBTYPES`, Conditions), `vessels.js` (sizes, classes, module roles/categories, size presets, crew posts), `features.js` (`FEATURES`, `CAMPAIGN_PRESETS`), `misc.js` (currencies, scales) — each an `export const` that `NIHILITY` references by shorthand (`DEFAULT_SPECIES_PRESETS,`), so `NIHILITY.X` reads exactly as before; these files are pure data and import nothing (keep it so: `constants.js` imports them at load time, a cycle would be a TDZ error). Edit a default catalog in its `defaults/` file. The split was checked by hashing the source of every export before and after (138 identical). When adding something, put it in the file of its kind and import siblings **directly** (`./catalogs.js`), not through the entry point — and keep the rule of no top-level code that calls a sibling, since these files import each other.

`NIHILITY` is one large exported config object (tiers, attribute keys/labels, effect targets, default currencies/species/damage-elements/status-conditions, etc.) plus `SYSTEM_ID`. Every GM-configurable *flat list* (id/label/+1-2 more fields per row) follows the same pattern: a `NIHILITY.DEFAULT_X` constant, a `getActiveX()` reader that does `setting-JSON > default`, a hidden `config: false` setting storing the JSON string, and an ApplicationV2 app built by `createListConfigApp({...})` in `module/apps/list-config-app-factory.js`. This covers currencies (`currency-config.js`), damage elements (`damage-elements-config.js`), and status conditions (`status-conditions-config.js`) — each of those files is now just a `fields`/`getActiveList`/`hint` config object passed to the factory, not a hand-written `ApplicationV2` class; **extend it the same way (add a `createListConfigApp` call) for any new flat GM-editable list.** Species presets (`species-config.js`) are the one exception — nested structure (body parts + racial skills per species) doesn't fit the factory's flat-row model, so it stays a hand-written app.

The factory takes an optional `afterSave` callback, which runs right after the setting is written. It exists for lists that something outside the `getActiveX()` reader has already copied: today only Status Conditions, which feed `CONFIG.statusEffects` (built once at `ready`) — without republishing there, the GM edits the catalog and the token HUD keeps showing the old palette until an F5. If you add a list whose values get cached anywhere else, wire it the same way instead of telling the user to reload.

**Atributos são renomeáveis, nunca re-chaveáveis** (`apps/attribute-config.js` + `getActiveAttributes()`/`getVisibleAttributes()`/`getAttributeLabel()` in `config.js`): the GM can change each combat attribute's **label** and hide it from the sheets, and that's all. The keys (`strength`, `magic`, …) are structure, not content — they appear inside already-saved Active Effect paths, in `EFFECT_TARGETS`, in `TITLE_BONUS_TARGETS` and in the vital-formula settings, so letting them be renamed would silently orphan every effect, Title and formula pointing at them. This is also why `AttributeConfigApp` is hand-written rather than built by `createListConfigApp`: the row set is **fixed**, and the factory's model is add/remove rows. Hiding an attribute is cosmetic only — a hidden attribute still counts in the HP/Mana formula, which is exactly the confusion the app warns about inline when the attribute is used by `getVitalFormula()`. **Percepção** (`perception`) is the eighth combat attribute, the counterpart of Furtividade: it rolls like any other attribute and accepts Title bonuses and Skill effects (it is in `EFFECT_TARGETS`, `TITLE_BONUS_TARGETS` and `EFFECT_TARGET_PATHS`). There is deliberately **no** contested-roll card — the system can't know who is opposing whom; the GM asks players to roll it. Existing characters start with 0 points in it and the pool budget did not change, so the GM hands out points with the extra-points field if wanted. Read labels through `getAttributeLabel(key)`, never `NIHILITY.COMBAT_ATTRIBUTE_LABELS` directly, or a renamed attribute shows its factory name in your UI.

`getResistanceTargetOptions()` (also in `config.js`) is the single source for the "Geral + each active damage element" dropdown shared by the Skill editor (`skill-editor-dialog.js`) and the Title sheet (`item-sheet.js`) — don't rebuild that list inline in a third place.

**Unlinked tokens are different people — compare Actors by `uuid`, never by `id`.** "Drone (1)" and "Drone (2)", two unlinked tokens of one Directory sheet, each have their own synthetic Actor: distinct `uuid`, **same `id`**. Anything that compared `actor.id`, matched `combatant.actorId`, or resolved a choice with `game.actors.get(id)` merged them — the target picker returned the Directory sheet (damage and conditions landed on the wrong actor), initiative rolled for the other token's combatant, the "Na cena" list showed one Drone. Use `sameActor`, `combatantIsActor`, `actorToken` (the token of *this* actor, preferring the selected/targeted one when a linked actor has several) and `actorDisplayName` (token name for unlinked) from config.js; store `uuid` in flags and dialog values and resolve with `fromUuidSync`. A linked token has the Directory actor's `uuid`, so linked duplicates still count once.

**Picking an Actor goes through one of two helpers, and which one depends on the question being asked:**
- `pickTargetActor({self, types, title})` (`module/helpers/target-picker.js`) is what every **Skill target** uses (Personagem and Nave sheets both). It layers three sources: an already-marked target on the map (`game.user.targets`) short-circuits the whole dialog, then short `<optgroup>`s (na cena / seus personagens / PJs) with `self` always present and pre-selected, and finally — only when the `allowOffSceneTargets` setting is on — a search-gated Directory group capped at 20 hits. This exists because a theatre-of-the-mind table (no map, no tokens) got an **empty** target list from the scene-only reader, which made the whole Resistência mechanic unreachable. Any new "who is this Skill hitting?" dropdown belongs here, not in a fourth hand-rolled list. Weapon attacks **and** Skill targets (both sheets' `_promptSkillTarget`) pass `preferMap: true`: with `allowOffSceneTargets` off and a scene open, the picker shows a banner and waits for a click on a Token (or the T key), with "Escolher da lista" as the way out — which is also how you target yourself without a token.
- `sceneActorCandidates({types, exclude, permission})` (`config.js`) remains the reader for the **scene-scoped** pickers — currency transfer, repair engineer/ship, PAD contact share — where "has a Token on the currently open scene" *is* the intended rule, never the whole Actor Directory. `pickTargetActor` builds its own "Na cena" group on top of it.

**Feature toggles (modularity) — `NIHILITY.FEATURES`.** The system is built to be reconfigured per campaign (medieval fantasy / sci-fi / mixed), and every switchable block lives in **one table**: `NIHILITY.FEATURES` in `config.js`, keyed by feature id, each entry carrying `setting` (storage key), `name`/`hint`, `default`, and optionally `parent` (a sub-feature is off whenever its parent is off). An entry can also carry `options` (`{settingKey: {label, hint, type: "number"|"boolean", default, min}}`): numeric/boolean fields that `FeatureConfigApp` draws under the toggle and saves, registered as world settings by the same loop and read through `getFeatureOption(featureKey, optionKey)` (falls back to the table default, never goes below `min`). Today only `movement` uses it.

Three things read that one table and nothing else, so **adding a block is a single new line there**:
- `registerSystemSettings()` registers one `config: false` world setting per entry in a loop.
- `FeatureConfigApp` (`apps/feature-config.js` + `templates/apps/feature-config.hbs`) renders the editor, nesting sub-features under their parent.
- `NIHILITY.CAMPAIGN_PRESETS` (Fantasia Medieval / Sci-Fi Arcano / Misto) maps feature id → boolean, applied in one shot by `applyCampaignPreset()`.

**Always read a toggle through `isFeatureEnabled(key)`**, never `game.settings.get` directly — only that helper walks the `parent` chain and falls back to the table's `default` when settings aren't registered yet (which really happens when a Data Model prepares early in the boot). The named shortcuts (`isEconomyEnabled`, `isVesselsEnabled`, `isSkillFusionEnabled`, …) all delegate to it; they exist because half the codebase already imported them.

**The rule that must never break: turning a feature off only hides UI and blocks creating *new* content of that kind — it never deletes, migrates or rewrites saved data.** Turning it back on has to return the world exactly as it was. That is what makes it safe to flip presets mid-campaign. Concretely: `vessels: false` blocks `preCreateActor` for starship/vehicle and hides the AI generation cards, but existing ships still open and work; `resistances: false` removes the Resistance section from the skill editor, and a Skill that already had `resistanceTarget` keeps it untouched.

There are **two** energy labels, not one: `getCharacterEnergyLabel()` (setting key `energyLabel`, default "Mana") for Personagem/Criatura and `getStarshipEnergyLabel()` (`starshipEnergyLabel`, default "Sistema Eletro-Plasmático (EPS)") for Nave/Veículo. Never hardcode "Mana"/"EPS" in a message — use `getEnergyLabelForActor(actor)`, which picks the right one by Actor type. `getStarshipEnergyAbbr()` (setting `starshipEnergyAbbr`, default "EPS") is the short form for the places where the full label would eat half the row — per-Módulo consumption lines and grid readouts on the ship sheet; use it there instead of the long label, and never a literal "EPS".

Render/action logs across every Sheet/App go through `debugLog()` (`config.js`), gated by the client-scoped `debugMode` setting (off by default) — use it instead of a bare `console.log` for anything that fires on every render/click; rare lifecycle events (system init, Compendium auto-created, migration completed) stay as plain `console.log`, no gate, since those are rare enough to always want visible.

`game.settings` scope matters here: AI provider/endpoint/model/API key (and `debugMode`) are registered `scope: "client"` deliberately (not `"world"`) — a `world`-scoped setting syncs to every connected client including players, which would leak the API key. Since only the GM uses the AI Assistant, client-scope solves this without any relay infrastructure, at the cost of needing to reconfigure per-browser.

## Data Models (`module/data/`)

- `character-model.js` — `CharacterDataModel` only. Player characters, NPCs, creatures and mounts are **all** `type: "character"`, separated by `isPlayerCharacter`; there is no second Actor Data Model (there was one, `CreatureDataModel`, never registered anywhere — it was removed rather than kept in sync for nothing).
- `starship-model.js` — `StarshipDataModel` and `VehicleDataModel`, both extending the shared `ShipSystemsDataModel` base (Porte/Módulos/Grid de Energia/cascata de dano/Tripulação — see "Sistema de Naves" below). Vehicle additionally has `fuel` plus `parts`/`speed` **getters** (`speed` is derived from the Motor Módulo, not a stored field); Starship additionally has `crew` (a plain capacity number, not the `crewMembers` roster) and a `maneuverability` getter, also derived from the Motor Módulo.
- `item-models.js` — `SkillDataModel`, `BodyPartDataModel`, `TitleDataModel`, `StarshipModuleDataModel`, `GenericItemDataModel`. Several small schema-builder functions (`grantedSkillSchema()`, `statModifiersSchema()`, `attributeBonusesSchema()`, `effectEntrySchema()`) are reused across multiple of these — read them before adding a new field so you reuse rather than duplicate. `grantedSkillSchema()` (Habilidade Concedida of Item Geral, Módulo and each Body Part modification) stores a **whole Skill**: `skillMechanicsFields()` — the same field set `subSkillSchema()` is built from — plus a flat `subSkills[]`. It used to hold only name/description/cost/tier, so the granted Skill arrived on the sheet with no mechanics at all. `buildGrantedSkillData` (`skill-snapshot.js`, pure, tested) turns it into the Skill that `createGrantedSkill` creates (always `active: false`, `isItemGranted: true`); it is edited through the same `openSkillEditorDialog` as any Skill, from the `nihility.grantedSkill` partial (`templates/parts/granted-skill.hbs`, registered on `init` through `registerSystemPartials` in `foundry-compat.js`), and saving it calls `refreshGrantedSkill`, which recreates the Skill on the Actor if the source is granting right now. Edits made to the granted Skill's copy on the Actor are lost when it is re-granted — the source's template is the truth. `TitleDataModel.resistances` (`[{target, amount}]`) is the Title-side half of the damage-resistance mechanic — see "Resistência/Imunidade" below. `effectEntrySchema()` is the shape of one entry in a Skill/Sub-Skill's `effects[]` array (`target`, `amount`, `durationRounds`, plus `conditionId`/`periodic`/`tickUnit`/`damageElements` — see "Status Conditions and periodic ticks" below).

**The `prepareDerivedData()` pipeline in `character-model.js` encodes the game's core balance rule and must run in this order:** `deriveCombatAttributes()` before `deriveVitalStats()` (the latter reads `combat.<attr>.total`, computed by the former). The rule itself, arrived at through several rounds of explicit correction, is a strict three-tier split per combat attribute:

- `attr.total = points + Title bonus` — the only permanent base, and the **only** thing that feeds the HP/Mana Max formula. The formula shape is fixed (`Atributo A.Total × Atributo B.Total × multiplicador`, with a floor) but **which** attributes, the multiplier and the floor are GM settings read through `getVitalFormula()` — defaults reproduce the historical `Força × Defesa × 10` / `Magia × Defesa Mágica × 10`, floor 50. Setting `energyPoolEnabled: false` (a campaign with no magic) zeroes `energy.max`/`value` outright and makes `useSkillEffect` charge no cost and `tickActorUpkeepSkills` drain nothing for Personagem/Criatura — the Skill still works, the resource simply stops existing. Ships are unaffected by that flag: their Grid is a separate system.
- `attr.effectiveTotal = total + buffDelta` (buffDelta = temporary Active Effects created by a Skill's `"temporary"` effect) → `attr.bonus = floor(effectiveTotal / 3)` → feeds the escalating dice pool in `dice.js` (+1d20 per +10 of bonus, all dice summed). Temporary buffs/debuffs affect rolls but never HP/Mana.
- `attr.itemBonus` (sum of `attributeBonuses` from equipped Items / installed Body Part mods) is computed but deliberately **excluded** from both `total` and `effectiveTotal` — it never touches HP/Mana and never escalates the dice pool. It's only ever added as a flat `extraFlat` number at roll time (`rollAttribute(actor, key, { extraFlat })` in `dice.js`), matching this system's pre-existing rule that weapon/equipment bonuses "somam por fora, na hora da rolagem."

Separately, permanent `statModifiers.{hp,energy}` (present on Skill, equipped Item, and installed Body Part mods) and the `hp`/`energy` `buffDelta` stack on top of the floored formula result with no ceiling/floor of their own. `Shield` (`attributes.shield.value`) is a flat, max-less resource that absorbs damage before HP when the GM clicks Aplicar in the chat (and can still be edited by hand) — conceptually and mechanically distinct from starship shields (`StarshipDataModel.shields`).

**Attribute Point pool** (same `deriveCombatAttributes()` pass): the GM grants a budget via two settings — `attributePointsStarting` (default 35) and `attributePointsPerLevel` (default 5) — and `dataModel.attributePointsPool = {total, spent, remaining}` is derived from them each prep. Allocation is two-phase on purpose: the +/- buttons on the sheet write to `attr.pendingPoints` (never counted in `total`/`bonus`/HP/Mana, only shown as `attr.previewBonus`), and only "Confirmar" (`confirmAttributePoints` in `actor-sheet.js`) moves them into `attr.points` in a single update. "Resetar" zeroes `pendingPoints` and never touches confirmed `points`. The GM can also grant extra points per character through `attributes.bonusAttributePoints` (a GM-only field under the pool banner; negative takes points back), which is simply added to `attributePointsPool.total` — the player sees only the bigger total, never a "from the GM" label; "Zerar pontos" leaves it alone. The GM-only "Zerar pontos (Mestre)" button (`gmResetAllAttributePoints`, shown only while the pool is enabled) is the escape hatch for a player who misallocated: it zeroes **both** `points` and `pendingPoints` on every attribute after a confirm dialog and whispers a Voz do Mundo note — level, Titles, Skills and Items are untouched, so the pool handed back is exactly what the current level grants. The + button is disabled once `remaining` hits 0. Note this makes `prepareDerivedData()` read `game.settings` — unlike the other config readers it is not wrapped in try/catch, so it assumes settings are already registered.


## Calendário e linhas do tempo (J9b)

`FEATURES.calendar` (filho de `worldClock`, `isCalendarEnabled()`); settings `calendarData` (catálogo, entra no Exportar/Importar) e `timelines` (estado do mundo, fora do Exportar/Importar: `transferableSettings` e `EXCLUDED_KEYS` o pulam). Leitores `getCalendar()`/`getTimelines()` ficam em `core/world-time.js` (memo pelo texto salvo), não em `config.js`; nunca altere o que devolvem. Ver [mundo.md](mundo.md).

- **1.120.0–1.121.0:** `core/config/defaults/species-elements.js` (puro, sem imports) tem os geradores das Linhagens por elemento do Dragoide/Slime, o Dragão de Trevas e o Slime Comum; `FANTASY_ELEMENTS_1120` (`defaults/elements.js`) tem Luz, Demoníaco, Terra e Vento; Regra da Mesa nova `predationFormsPercent` (`getPredationFormsPercent`).
