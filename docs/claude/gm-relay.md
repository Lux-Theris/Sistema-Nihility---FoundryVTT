# Escritas em nome do Mestre (gm-relay) e efeitos em Atores alheios

> Parte do guia do projeto. O índice e as regras que valem em todo lugar estão no `CLAUDE.md` da raiz. Quando o texto diz "abaixo"/"acima" ou cita uma seção que não está aqui, procure-a pelo índice.

## Escritas em nome do Mestre — `helpers/gm-relay.js`

`system.json` had declared `"socket": true` since forever with nothing using it; this is the first and (so far) only use. The problem it solves: whoever rolls an attack is almost never the owner of the target's sheet — a player attacking another player, or attacking an NPC — and `item.update()` on someone else's document simply fails. Before the relay, Resistance XP was credited only when the GM personally rolled, which left half the situations at the table with no progression at all.

`runAsGm(action, payload)` executes the action directly when the caller already *is* the designated GM, and otherwise emits it on the socket; `registerGmRelay()` (called on `ready`) listens. **Where actions live (since the relay split).** `helpers/gm-relay.js` is only the engine: the socket, `runAsGm`, `isDesignatedGm`, the gates `owns`/`ownedDoc`/`mayActFor`/`actorsOwnedBy` (exported for the subsystems) and an internal `HANDLERS` map that starts empty. It imports **no subsystem**. Each subsystem exports its own actions as `export const RELAY_HANDLERS = { name: async (payload, user) => {…} }` (an object of functions only — nothing is called at module top level). `core/relay-actions.js` imports every `RELAY_HANDLERS`; `registerAllRelayActions()` feeds them to `registerRelayActions(handlers)` (throws on a duplicate name or a non-function value; the check is the pure `validateRelayRegistration` in `gm-relay-rules.js`) and then compares the result with `RELAY_ACTION_NAMES` (`core/relay-action-names.js`, pure, alphabetical, frozen by a test). Anything missing or extra is shown to the GM on screen with `reportError(..., {gmOnly: true})` instead of a request failing silently. The entry point calls `registerAllRelayActions()` right before `registerGmRelay()` in `ready`, and it is the only importer of `relay-actions.js` (a subsystem importing it would create a cycle).

**To add a new action:** (1) write the handler in `RELAY_HANDLERS` of the subsystem it belongs to, importing `mayActFor`/`ownedDoc`/`owns`/`actorsOwnedBy` from `helpers/gm-relay.js` and `refuse`/`RELAY_REASONS` from `gm-relay-rules.js`; (2) add its name to `RELAY_ACTION_NAMES` in alphabetical order and to the frozen list in `test/gm-relay.test.mjs`; (3) if the subsystem file is new to the relay, import its `RELAY_HANDLERS` in `core/relay-actions.js` and add it to `ALL_HANDLERS`. Then apply the three rules below.

Three rules to keep for every action:
- **Check who asked.** Every handler is called as `(payload, user)`. `user` comes from the socket callback's second argument, which the Foundry **server** fills with the sender's session user (`handleCustomSocket` → `emit(channel, data, socket.user.id)`, verified in 14.368) — never from a payload field, which the client could forge; a message without it is refused. On the direct path it is `game.user`. Gate on ownership of the action's **origin** document with `owns`/`ownedDoc`/`mayActFor` (the GM always passes): the attacking Actor, the Skill's owner, whoever cast the Zone/Structure, the ship that owns the tractor module. Until 1.63.2 there was no such check and any player could, from the console, delete anyone's Zones, damage any Structure, fill anyone's Resistance XP or push arbitrary Skills into the Compendium. Two actions are asked for by the *attacker*, who rarely owns the target, so they are bounded instead of gated: `resistanceXp` (only real Resistance Skills, once each per request, at most the XP of a hit that took the target's whole Vida) and `resistanceExposure` (≤ 10 distinct element strings; the worst case is a suggestion to the GM). `registerCompendiumItem` uses the payload only to *find* the Item (by `_id`, on an Actor the sender owns) and registers that Item's own data.
- **The handler runs with GM permission, so treat the payload as untrusted.** Resolve UUIDs and validate everything on the GM side; never accept a number the sending client could have inflated. The XP `gain` is computed by the sender for convenience but re-clamped to the level cap at the destination — copy that pattern.
- **Only the *designated* GM executes** (`isDesignatedGm()` = Foundry's own `game.users.activeGM`: highest role, then lowest id — until 1.77 it was "lowest id" alone, which could disagree with the core's turn events when a GM and an Assistant were both online). It is exported for hooks that fire on every client (like `moveToken` in `movement.js`) and must write from exactly one of them. **Never use `game.user.isGM` as the "who executes" guard of a hook that writes** — it is true for every GM and Assistant connected; the start-of-turn `updateCombat` hook, `runMigrationIfNeeded` and the XP-ready announcement all had that bug until 1.78. With two GMs online, without this both would run the same handler and the XP would be credited twice.

With no GM connected the action is dropped silently, on purpose: this is called in the middle of damage resolution, and a warning on every single hit would be worse than the lost XP.

**Except where the player waits to see something (1.78):** `runAsGm(action, payload, {reply: true, timeout})` returns `Promise<{ok, reason}>` and never throws — `noGm`, `timeout`, `permission`, `invalid`, a handler error's message, or a reason string the handler returned (`refuse(reason)` / `false`). The designated GM answers on the same channel `{relayReply, replyTo, requestId, ok, reason}`; `replyTo` comes from the server-filled sender, and the requester only accepts a reply addressed to it and sent by a GM. Pure part in `helpers/gm-relay-rules.js` (`normalizeRelayOutcome`, `relayFailureMessage`, `createReplyRegistry`, tested). Used by `createStructure`, `createZone` (the "criou a zona" card and XP only go out when it worked), `setShieldLight` (one warning per 3 s, so an Emission doesn't spam), `setMovementDash`, `engageTractor` and `applySkillEffects`; `timeout` counts as done (the GM may just have been slow). A reply is only ever a UI hint, never proof of anything. Background writes (XP, exposure, damage to structures) stay fire-and-forget.

**Efeitos de Skill em Atores alheios (1.79.0).** A player putting Lentidão on an NPC, a buff on another player's character or an Emission with an NPC inside used to get "Falha ao usar a Habilidade", sometimes with half of it applied, because Foundry refuses the write. `applyEffectsToTargets` (skill-effects.js, used by `applySkillEffects` and `applySkillEffectsArea`) splits the targets with `splitByWriteAccess` (`target.isOwner`): owned ones are applied locally as before, and the rest go in **one** `applySkillEffects` relay request with `reply: true`. The GM side, `applySkillEffectsAsGm`, **rebuilds the mechanic from the Skill (or consumable) on the sheet**, never from the payload, and the requester must own it. From the client it takes only the targets, the Mana-investment power (clamped to 0.01–1000) and the parts chosen at use time (`normalizeEffectRequest`/`applyEffectChoices`, pure, in `skills/effect-relay-rules.js`, tested). It returns each target's summary and XP measures, and the requester posts the card and credits the XP. Behaviour without a GM: a single target gets a warning and no card, and returns `false`, so a consumable isn't spent. In an area, the owned targets still get the effect and the others' row says "não aplicado". This is the same model as dnd5e/Midi-QOL, where whoever has the permission writes. Desfazer uso works on these uses too.
