# Skills: criação, uso, Ativa, Recarga, Preparo, Escudo, Mana variável, hotbar e editor assistido

> Parte do guia do projeto. O índice e as regras que valem em todo lugar estão no `CLAUDE.md` da raiz. Quando o texto diz "abaixo"/"acima" ou cita uma seção que não está aqui, procure-a pelo índice.

## Skill mechanics: creation vs. runtime use

These are two separate files with two separate concerns — don't conflate them:
- `skill-economy.js` handles Skill **creation/lifecycle**: fusion (`fuseSkills`, tier-consumption rule via `canConsumeTier` — a skill can only consume sources of its own tier or lower), the Skill Point economy (break/merge/request/approve/reject, gated behind GM chat-message approval buttons), Item/Module-granted skills (`createGrantedSkill`/`removeGrantedSkill`, marked `isItemGranted: true` so they can never be fused and vanish automatically when their source is removed). Skill/Compendium creation itself is delegated to `compendium.js` (`ensureSystemCompendiums`/`registerItemInCompendium`/`getCompendiumForItemType`); the Sub-Skill-snapshot logic shared by manual fusion and AI-generated Skills lives in `skill-snapshot.js` (`buildSubSkillsFromSources`), kept separate specifically to avoid a circular import between `skill-economy.js` and `ai-generation.js` (see "AI integration and the ai-helper.js split" below — this used to be one 1166-line `ai-helper.js` file before the module was split apart).
- `skill-effects.js` handles **using** an already-created Skill (`useSkillEffect`): `effectType: "damage"` rolls the skill's free-form `damageFormula` (any Foundry dice syntax) and posts publicly, tagged with 0+ `damageElements` (which split the damage and carry on-hit effects — see "Dano por elemento" below); `effectType: "temporary"` applies each entry in `effects` as either a duration-bound `ActiveEffect` (targeting the `buffDelta` schema paths — this is how temporary buffs/debuffs/drawbacks are implemented), a direct Shield add (no duration), or a **periodic** tick (see immediately below).

**Fusão vs. Evolução** are two different lifecycle operations, both in `skill-economy.js`: `fuseSkills` consumes 2+ Skills into one whose `subSkills[]` are frozen mechanical snapshots of the consumed sources (always flattened — fusing a fusion inlines *its* components, never nests); `evolveSkill` is 1-to-1 — the old Skill leaves no component behind, only an `evolvedFrom` string. Both preserve the originals in the Compendium before removing them from the Actor. Both are reachable from the Actor sheet and, for Evolução, also from the Item sheet. **Fusão and Evolução are GM-only**: the buttons are hidden from players, both sheet handlers bail on `!game.user.isGM`, and `evolveSkill` itself throws for a non-GM — a player's route to a new Skill is the Skill Point request, never rewriting one they own.

**Armas de Personagem** are not a new Item type: `GenericItemDataModel.weapon` (`enabled`/`damageFormula`/`scalingAttribute`/`isMagicDamage`/`damageElements`) turns any Item Geral into a weapon, which puts an "Atacar" button on its row in the Actor sheet — **only while the Item is `equipped`** (a disarmed/backpacked weapon can't attack; same "counts only while equipped" rule as `attributeBonuses`/`statModifiers`/`grantsSkill` on the same Item) — (`attackWithWeapon` → `useWeaponAttack` in `damage-roll.js`). It builds a synthetic `mech` and goes through `rollSkillDamage`, so Escala por Atributo, Defesa Mágica, Resistência, the ship cascade and the Aplicar-dano chat buttons all apply exactly as for a damage Skill. No level, no energy cost, single target only (an area weapon is a Skill). Ship weapons are a separate thing — see "Armas" under Sistema de Naves.

**Sub-Skills are usable at runtime, not just history.** `subSkillSchema()` carries the full mechanical field set of a real Skill (tier/level/cost/upkeep/animation/resistance/effectType/damageFormula/effects/targetType/area). When a Skill has Sub-Skills, "Usar Habilidade" first prompts which component to fire (`_promptSubSkillChoice` in `actor-sheet.js`), and `useSkillEffect(..., {subSkillIndex})` then resolves that component's own mechanics instead of the parent's — modelled on Tensura's umbrella Unique Skills. Each Sub-Skill also toggles its own `active` state independently (`activeStatePath(subSkillIndex)`), so one fused Skill can have several Active components running at once.

**Emissão (area targeting)** — `targetType` on a Skill (and on each Sub-Skill) is `"targeted"` (the default: pick one Actor from a dropdown) or `"emission"`, which instead has the user place a shape on the canvas and affects everyone inside it. All the canvas work lives in `module/combat/area-effects.js` and **nowhere else** — `skill-effects.js` and the sheets only ever receive an already-resolved `Actor[]`. **V14 removed Measured Templates** (the document type and `canvas.templates`), so nothing here depends on them any more: the area is a plain object in scene pixels (`{shape, x, y, radius, angle, direction, width}`, same conventions as a template — direction 0 = east, clockwise), the placement preview is our own `PIXI.Graphics` in `canvas.controls` (the same approach as Structure placement), and "who is inside" is pure geometry (`module/combat/area-geometry.js`: `areaFromSkill`, `areaContains`, `areaPolygon`, tested) — never a template's/Region's `shape`. Only the document a **Zona** leaves on the scene differs by version, chosen by `zoneDocumentData(area, {generation})`: a `Region` on V14 (circle as a circle, cone/line as a polygon built from the same geometry, so what is drawn is exactly what is tested) and a `MeasuredTemplate` on V13. The area is stored in the zone flag (`zone.area`), validated GM-side by `normalizeArea`; V13 zones from before 1.63.1 (no `area` in the flag) are read back from the template's fields (`areaFromTemplateData`). `zonesOnScene` reads `scene.regions` (plus `scene.templates` only below V14, to avoid deprecation warnings), and zone ticks compute token centers from the document (`tokenDocCenter`), so they no longer need the GM to be viewing the combat's scene. A Zona's rounds count down at the start of **its caster's** turn (`advanceZones`), not at the round change — the round turns over at the top of the initiative, rarely the caster, and a 2-round Zone used to vanish before the caster's second turn; a caster who is not in the combat falls back to the round change. Shapes are `circle`/`cone`/`ray` (`areaShape`), sized by `areaDistance` and, for cones, `areaAngle`; mouse wheel rotates cone/ray (Shift = finer step), left-click confirms, right-click/Esc cancels, Shift while moving disables grid snapping. The cone's apex and the line's start don't count as inside (the caster stands there). `areaEffectsSupported()` (an open scene on the canvas) is the guard the sheets check before offering it. On the effect side, area versions roll the damage **once** and apply each target's own reductions to that same total (`rollSkillDamageArea`/`applySkillEffectsArea`), reporting everything in one consolidated chat message.

**Quem a área atinge** (`areaAffects` in `usageFields()`, 1.89.2; in every copy list next to `areaFreeLevel`): `all` (default, also what a Skill saved before means — a Fireball at your feet burns you) / `notCaster` / `allies` (caster + same Token disposition) / `enemies`. Pure rule `areaAffectsTarget` (area-geometry.js, tested), applied in `pickAreaTargets(skill, reach, {caster})` (Emission and thrown consumables) and in `tickZonesForCombatant` (the caster's side is the disposition of their Token on the zone's scene, else `zone.casterDisposition` stored at creation). **An area never hits the dead** (`isDead`), in any mode; a single target still can (resurrection).

`isMagicDamage` (boolean) is independent of `damageElements` (array) — a skill can be magical with no element (pure arcane force), elemental with no magic tag (e.g. a flaming sword dealing physical damage), or both. Only `isMagicDamage` gates the Defesa Mágica reduction below; elements drive the per-element split, Resistência and on-hit effects described in "Dano por elemento".

**Magic damage reduction**: when a damage Skill has `isMagicDamage: true` and is used against a target, `rollSkillDamage` reduces the roll by `clamp(target.system.attributes.combat.magicalDefense.total × NIHILITY.MAGIC_DEFENSE_REDUCTION_PER_POINT, 0, NIHILITY.MAGIC_DEFENSE_REDUCTION_CAP)` — a percentage (not a flat number), so it stays relevant at every level range the same way the HP/Mana formula's multiplicative scaling does. Tune the two constants in `config.js`, not the formula shape, if this needs rebalancing. Target selection is now prompted for **any** `"damage"` skill (not just magic ones, unlike before Resistance existed) — even a purely physical hit needs a target so the Resistência mechanic below has someone to check.

**Resistência/Imunidade** (`module/combat/resistance.js`): a Skill can be a passive damage-reducer instead of (or as well as) anything else, via `system.resistanceTarget` — `""` (not a resistance skill), `"general"` (reduces *any* damage), or a damage-element id (reduces only that element/type — `"physical"` covers cuts/blunt trauma, already one of the default damage elements). Progression is fixed at 10%/`level`, but the ceiling differs by target: **General caps at level 5 (50%) and never becomes "Imunidade Geral"** (full immunity to everything would be too strong) — only an Elemental resistance reaches level 10/100% and auto-renames itself from `"Resistência: {Elemento}"` to `"Imunidade: {Elemento}"` (`computeResistanceName`/`computeResistancePercent`/`resistanceMaxLevel`, all exported from `skill-effects.js`). The rename only happens at two triggers — picking a Category in the item sheet, and clicking Level Up — never from an arbitrary edit of the level field, so a custom name isn't silently clobbered. Titles can *also* grant Resistance (`TitleDataModel.resistances`, a flat GM-typed percentage with no level formula, since Titles don't have levels) — for the same target, Skill and Title resistance **add together**; duplicate sources of the same kind (two Skills, or two Titles, for the same target) only count the best one, not the sum. `applyDamageReductions` no longer chains every element's Resistance over the whole hit (that made Fogo+Gelo against someone immune to Fogo deal 0) — see "Dano por elemento" below.

Both damage paths report the **final** (already reduced) number in chat, never how much was reduced nor that a reduction happened at all: single-target appends `— {Alvo}: {n}` to the roll flavor, area lists one `{Alvo}: {n}` row per target. The raw roll is still visible because `roll.toMessage()` shows it — that is intentional (the dice are public, the target's defenses are not). Keep the two paths reporting the same way; they silently disagreed once and Resistência ended up meaningless against single targets for a long time.

**Status Conditions and periodic ticks** (`module/skills/effects-apply.js`, schema in `effectEntrySchema()`): an entry in a `"temporary"` Skill's `effects[]` can carry an optional `conditionId` (id from `getActiveStatusConditions()`/`config.js`'s GM-editable catalog — Cegueira, Veneno, Queimadura, Lentidão, etc., each a label + icon plus an optional **default effect**, see below; picking one gives the created `ActiveEffect` a Foundry `statuses` entry so it shows the token overlay icon, but **nothing about a Condition blocks an action by itself** — the GM adjudicates what "cego"/"atordoado" prevents at the table, same as the rest of this system's philosophy of computing numbers, not enforcing turn economy). Separately, `periodic: true` (only meaningful for `target: "hp"` or `"energy"`) turns the entry into a damage/heal-over-time tick instead of a one-shot buff: `durationRounds` becomes "how many ticks remain," and `tickUnit` picks how it advances — `"combatRound"` ticks itself via the `updateCombat` hook whenever it becomes that Actor's turn (GM-only execution, guarded so multiple connected clients don't double-apply it), `"manual"` waits for a click on the "Aplicar Tick" button next to the Condição Ativa chip on the Actor sheet header (covers long-term healing/damage outside combat, e.g. "Regeneração Amorfa" ticking once per rest, without needing any game-time/calendar system).

Reapplying the exact same named Condition (same `conditionId`) onto a target that already has it **refreshes** the existing `ActiveEffect` instead of creating a second one (`findStackableEffect`, matched on `conditionId` + same periodic-ness): the duration/ticks become the larger of what was left and the new duration, and a periodic tick keeps the **stronger** value (`refreshReapplication` in `damage-rules.js`). It used to *add* durations (5 + 10 = 15 rounds); the owner decided that reapplying only refreshes, so a weak hit can never weaken a strong Queimadura nor stack an endless one.

**Condition default effect** (`effect` on a catalog entry, edited in the card editor `apps/status-conditions-config.js`): `kind: "tick"` (damage/heal per round on Vida or Mana, value `fixed`, `hitPercent` — % of the damage of the hit that applied it, the default, so a 5000 hit burns proportionally instead of 5 per turn — or `maxPercent`) or `kind: "modifier"` (an attribute, fixed or %, or `movement`, always %, e.g. Lentidão −50% Deslocamento through the `attributes.movementPercent` field). `resolveConditionEffect` (pure, tested) turns it into a concrete effect entry. It is used whenever a Condition arrives **without its own value**: a damage element that applies it, a Skill effect entry with the Condition and amount 0, or the GM marking it on the token (the manual dialog offers "usar o efeito padrão" plus a "dano do golpe" field for `hitPercent`). With `hitPercent` and no hit to take it from, the Condition is only the icon.

A damage tick (`tickAmount < 0`) is reduced by the target's Resistência Geral + Resistência Elemental (per `damageElements` chosen on that effect entry) exactly like `rollSkillDamage`'s reduction — **except it deliberately skips Defesa Mágica entirely**, even for a "magical" Veneno; this is a one-off balance call (Veneno Mágico bypasses Defesa Mágica on purpose), not a bug, so don't "fix" it back to match `rollSkillDamage`'s pipeline without checking with the GM first. A heal tick (`tickAmount > 0`) is never reduced by anything — there's no "resist your own healing" concept anywhere in this system.

**Habilidade Ativa** (`hasUpkeep`/`upkeepCost`/`active`, shared by `SkillDataModel` and `subSkillSchema()` via the `usageFields()` builder in `item-models.js`): a Skill can be a toggle instead of (or as well as) a one-shot use. `cost` (the pre-existing field) is spent once when turning it on; `upkeepCost` then drains every round while `active` stays true, via `tickActorUpkeepSkills` (`skills/upkeep.js`) — called from the same `updateCombat` hook as `tickCombatRoundEffects`, so both fire once per combatant's own turn, GM-only. **The one-off `cost` and the per-round `upkeepCost` are spent through two completely different mechanisms** — this split is the whole design, don't collapse it:
- **One-off `cost`** comes from a *persisted* field (`energyValuePath`/`currentEnergyValue`): `attributes.energy.value` for Personagem/Criatura, `powerGrid.capacitor.value` for Nave/Veículo. It must be persisted — this used to point at `powerGrid.reactorOutput`, which `prepareDerivedData()` recomputes from the Reator Módulo every prep, so the deduction was overwritten on the next preparation (ship skills were free) and a ship with no Reator read 0 and could never pay anything. `capacitor.max` is always derived and **never zero**: with no Bateria Módulo it falls back to the Porte row's `conduitCapacitor` — the charge already sitting in the hull's own power conduits — and installing a Bateria **replaces** that value rather than adding to it. Every default conduit value is deliberately kept below 125 (the capacity of the smallest installable Bateria, Compacto) so that replacing is never a downgrade at any Porte; `test/ships.test.mjs` locks that invariant, so raising a conduit value fails the suite instead of silently making a Bateria an upgrade that isn't one.
- **Per-round `upkeepCost`** is *not written anywhere* for ships. `ShipSystemsDataModel.activeUpkeepDrain` sums the upkeep of every Active Skill/Sub-Skill and `prepareDerivedData()` subtracts it from the Reactor's generation: `powerGrid.reactorOutput = reactorBaseOutput - activeUpkeepDrain`. The Skill's own `active` flag *is* the persistence, so switching it off returns the energy with no compensating write to get wrong. `tickActorUpkeepSkills` then only enforces the ceiling for ships (`enforceShipUpkeepCapacity`): Skills whose combined upkeep exceeds `reactorBaseOutput` get force-deactivated, in sheet order. Personagem/Criatura keeps the original behaviour (`drainCharacterUpkeep` really subtracts from the pool, one source at a time, since order matters when there isn't enough for all). Energy hitting 0 mid-upkeep force-deactivates the Skill (`warnInsufficientEnergy` whispers only the user who tried to act). Toggling a `"damage"`-type Active Skill off never re-prompts for a target (`isDeactivating` short-circuit in both `actor-sheet.js#onUseSkill` and `starship-sheet.js#onUseSkill` — deactivation is symmetric with whatever target it was originally applied to, not a new action).

Reapplying (re-toggling on) an Active Skill whose `effects[]` include a duration-bound buff or a periodic tick must never let the reapplication silently extend/refresh what's already running — the **anchor** mechanism in `applyEffectsToActor`/`tickPeriodicEffect` (`skills/effects-apply.js`) exists specifically for this: each created `ActiveEffect`/periodic tick records which Active Skill "anchors" it, and turning the same Skill off is what actually lets it expire/removes it (`removeUpkeepLinkedEffects`) — not a fixed duration ticking down independently of the toggle state. A periodic (Veneno/cura) entry's `displayTicks` being `null` means "until deactivated," rendered as such in the Condição Ativa chip, rather than a numeric countdown.

**One lifetime model for both kinds of effect** (`module/combat/effect-anchors.js`, pure, tested): an effect — plain buff/debuff *or* periodic — lives while it has **at least one anchor OR finite time left**. Every Active Skill that applies the same named Condition adds its own anchor to `activeAnchors`; switching one off removes only that one. Anchors identify the Skill by **uuid** (`skillUuid`) — two unlinked Drones share Skill ids, so the old id-only match let one Drone's toggle strip the other's effect. A plain effect being held by an anchor has **no Foundry duration** (it would expire with the Skill still on); the finite time of ordinary applications of the same Condition runs in parallel in the `finite` flag (`{rounds, fromRound, combatId}`, -1 = permanent) and is restored as a Foundry duration when the last anchor leaves. Reapplying with 0 rounds is permanent and beats any finite time (`refreshFiniteRounds`). Legacy effects (`tiedToActive` + `sourceSkillId`, no list) are read through `effectAnchors(flags, effect.origin)` — never read `activeAnchors`/`tiedToActive` directly. Release (`removeUpkeepLinkedEffects`) visits only the actors the Skill anchored: since 1.78 the actor that **holds** the Skill keeps the flag `anchoredTargets` (a list `[{skillUuid, sourceSkillId, sourceSubSkillIndex, targets[]}]` — a list, not an object keyed by uuid, because `setFlag` would expand the dots of a uuid; pure helpers `recordAnchoredTarget`/`anchoredTargetsFor`/`forgetAnchoredTargets` in effect-anchors.js; capped at 200, past which it falls back to the scan). Without a record (Skill switched on before 1.78) it still scans the Directory **and** unlinked tokens' synthetic actors of every scene (`worldActors`, `helpers/world-actors.js`). It writes on the actors the user owns and sends the rest to the GM (`releaseSkillAnchors` relay with `targetUuids`, which refuses while the Skill is still active). Known limit: an Active **Zona** Skill switched on before 1.78 that re-applies afterwards records only the new targets — switching it off and on once fixes it.

**Mana variável** (`variableMana` in `usageFields()`, so Skill, Sub-Skill and Habilidade Concedida all have it; the snapshot/copy lists in skill-snapshot.js, skill-economy.js and actor-sheet.js carry it): `useSkillEffect` asks how much to invest (`promptManaInvestment`, `apps/mana-invest-dialog.js`; or `options.manaInvested`), charges that instead of the Custo, and turns `r = invested ÷ cost` into power with `manaInvestmentPower` (config.js, pure, tested): `r` below 1, `r^k` above — **no ceiling on purpose** (the owner wants the "all my Mana in one explosion" character rewarded), but each extra point is worth less, so the giant blast is inefficient per Mana. `k` and the minimum % are world settings (Regras da Mesa, group Vida e Energia, named "Custo variável" because the energy label is configurable and setting names are fixed at registration). The power travels as `mech.investPower` on a plain copy of the mechanic and multiplies alongside the level Power in `rollSkillDamage`, `rollSkillDamageArea` and `applyEffectsToActor`, and scales a Estrutura's Vida (`power` in the relay payload, clamped GM-side). An Active Skill stores the ratio in `investRatio` when switched on, and `collectActiveUpkeepSources` multiplies the upkeep by it. Ships never use it (they pay from the Bateria). Known limit: a non-Active **Zona** re-resolves the Skill at each tick and does not keep the investment.

**Recarga, Preparo e investir além da Mana (H3 + C2, `skills/cooldown-rules.js` pura/testada, `skills/preparation.js`).** Campos `cooldown`, `prepTurns` (editáveis, 0 = off) e `cooldownRemaining` (estado) em `usageFields()`, logo em Skill, Sub-Skill e Habilidade Concedida; os dois editáveis estão em todas as listas de cópia (skill-snapshot, evolução, `REQUEST_MECHANIC_FIELDS`, `sanitizeSkillMechanics`, editor rápido, aba Geral da ficha). Tudo conta em **turnos do dono, só em combate começado** (`inStartedCombat`): fora dele nada bloqueia nem é gravado, e um Preparo fora de combate dispara na hora pagando tudo. `tickSkillTimers` roda no `updateCombat` do Mestre designado logo depois do Vida 0 (não para morto).
- **Recarga N:** gravada **depois do uso** (`applyCooldownAfterUse`, dentro do `recordSkillUse`, então o Desfazer a leva) como `cooldownToStore` = N + 1 turnos "até poder usar"; cai 1 no começo de cada turno do dono → usada na rodada 1 com recarga 1, bloqueada na 2, livre na 3 (cai a cada N+1 rodadas). Sub-Skill regrava a lista (`skillStateUpdate`). Zera no `deleteCombat` (`endCombatTimers`) e no Descanso. Bloqueio: `useBlockReason` em `useSkillFlow` (antes de pedir alvo; vale para ficha, Nave e hotbar) e de novo em `runSkillEffect`; desligar uma Ativa nunca é bloqueado. A ficha mostra o botão Usar desligado com "recarga N"/"preparando (N)" (`skillTimersFor`, mapa `skillTimers`).
- **Sobrecarga:** `r` = investido ÷ Custo; `r` > 2 soma `⌈(r − 2)² × k⌉` rodadas de recarga (`overchargeExtraCooldown`; `k` = setting `manaInvestOvercharge`, Regras da Mesa, grupo "Custo variável", padrão 1, 0 desliga). Uma Skill sem recarga ganha uma.
- **Preparo N** ("fica pronta em N rodadas"): `preparationPayments` divide o Custo (com o investimento) em N partes; a 1ª sai ao começar e as outras no começo de cada turno de preparo; no turno seguinte à última parte dispara **sem pagar de novo** (`options.prepaid = {ratio}` → `useSkillEffect` pelo caminho normal, XP por uso e recarga no disparo). Faltou Mana numa parte → falha e o pago se perde; Caído/Inconsciente/morto cancela (gancho `createActiveEffect` de incapacitation.js); Supressão (Antimagia para mágica, PEM para tecnológica) no começo do turno falha (qualquer nível, sem comparar com o da Skill). Estado: lista no flag `preparing` do Ator (`{id, skillUuid, skillId, subSkillIndex, label, turnsLeft, payments, paid, investRatio, options, effectId}`; `options` = `packUseOptions`: alvos por uuid, área/origem, posição, rolagem; escolhidos ao COMEÇAR) + um Active Effect "Preparando: X" cujo número no Token é `turnsLeft` (tom `prep` em effect-badge-rules; não entra no Fim do combate). O Painel do combate lista "preparando X (N)". O disparo roda no cliente do Mestre (prompts de foco de cura/parte aparecem nele). Preparo não aceita investir além da Mana (o Custo é pago aos poucos). Desfazer: `system.cooldownRemaining`, `subSkillsCooldown` e o flag `preparing` entram na fotografia.
- **Investir (C2):** no diálogo do Shift+clique (`promptRollOptions({invest})`) toda Skill com Custo > 0 que não é Descritiva, sem Mana variável e de Personagem ganha "Investir Mana" (piso = Custo, teto = `investCeiling` = 2× Mana máxima); sai como `options.manaInvested` e usa `manaInvestmentPower`. Skills com Mana variável mantêm o diálogo próprio (mínimo dele), agora com teto de 2× a máxima. Investir acima da Mana atual (`overdrawInfo`) pede confirmação (`confirmOverdraw`), a Mana vai a 0, o efeito sai com a força de tudo, e **depois** (qualquer resultado) um d100 público com "+N% além" (em % da Mana que tinha; com 0, da máxima) e `knockUnconscious` (Inconsciente pelo contador `wakeRounds`, mínimo 1). Nave nunca (paga da Bateria). O Mestre decide o bom/ruim do d100; o sistema só mostra.
- **Simulador:** `attackCadence`/`attackReady`/`cadenceFactor` (encounter-rules.js): Recarga N cai a cada N+1 rodadas, Preparo N cai pela 1ª vez na rodada N+1 (período `P + (C > 0 ? C + 1 : 0)`); fora da rodada o ataque de reserva age. A frase da Skill ganha "recarga N" e "pronta em N rodadas"; o aviso do editor tem "Preparo numa Ativa" (soft) e valores negativos (hard); a sugestão de Custo não muda (o Preparo só parcela o mesmo Custo).

**Escudo pessoal em pools** (`attributes.shield.pools`, `module/combat/shield-pools.js`): every Skill that gives Escudo owns a pool on the target (`{holderUuid, skillId, subSkillIndex, value, order}`); `shield.value` stays the **total** shown on the sheet, and whatever exceeds the pools' sum is the "avulso" (typed by hand, or from before pools). Damage (`consumeShieldPools`, pure, tested) spends **the most recent pool first** (owner's decision), avulso last, and **Penetration acts on every pool in turn** — each layer lets the penetrated fraction through, which meets the next layer and is split again; under 1 is discarded. The personal-shield penetration is computed in `applyDamageReductions` (element penetration weighted by each part's damage, plus a ship weapon's penetration against a person) and travels in the damage card (`shieldPenetration`); the card also stores `previousPools` for Desfazer. A total changed without touching pools (sheet field, negative Effect, rest) is reconciled in `preUpdateActor` (`reconcileShieldPools`: lowering takes from the newest pool, raising becomes avulso). Shield lights became a **stack** per token (`shieldLight.stack`, the newest pool's light shows); a pool that ends drops only its own light (`syncShieldLightsToPools`).

**Escudo mantido** (ex.: Barreiras Múltiplas — `shieldRegen`/`shieldCap` on an effect entry with target `shield`, only meaningful in an Active Skill): activation adds the amount up to the cap (`sustainedShieldGain`, pure, tested — a cap limits the *total* Escudo; shield from other sources above it stays, it just doesn't regenerate), each start of the **holder's** turn regenerates it (`regenerateSustainedShields`, called from `tickActorUpkeepSkills` after the drain, so a Skill that just fell for lack of Mana doesn't regenerate), and switching the Skill off removes that Skill's **pool** from each target (`removeShieldPool`); the cap applies to the Skill's own pool. The records live on the Actor that **holds** the Skill (flag `sustainedShields`, target by uuid), because it's that Actor's turn and that Actor's toggle that drive them, and the shield can be on an ally. Level Power scales `amount`, `shieldRegen` and `shieldCap` alike.

**Animação** (`animationPath`, same `usageFields()` builder): an optional Sequencer effect path played by `playSkillAnimation()` (`module/core/vfx.js`) whenever `useSkillEffect` fires — `vfx.js` is a soft dependency (`sequencerAvailable()` checks `typeof Sequence !== "undefined"` and no-ops entirely if the Sequencer module isn't installed/active), fire-and-forget (never awaited by the calling effect logic, so a slow/missing animation never blocks the actual mechanical resolution).

Racial-tier skills only ever come from a Species preset (never bought with Skill Points); Ultimate-tier only ever comes from fusion (never bought directly) and is hidden from players in tier dropdowns/lists until they own one — but always visible to the GM (every tier-visibility filter in the sheets is `tier !== "ultimate" || game.user.isGM` or equivalent, deliberately).

**Level Up is GM-only**: the Nível field is `readonly` for non-GM on both the Actor sheet (`system.attributes.level`) and the Skill item sheet (`system.level`) — the only way either goes up is the GM-only "+" button next to each (`levelUpActor` in `actor-sheet.js`, `levelUpSkill` in `item-sheet.js`). Both announce via "Voz do Mundo" (actor level-up reuses the pre-existing `announceLevelUp`; skill level-up is a new `kind: "skill-level-up"` call). `levelUpSkill` also refuses to increment past a Resistance skill's `resistanceMaxLevel` (5 or 10) instead of over-leveling it silently.

## Skills e armas na hotbar, e a Skill numa frase

**Hotbar (H14, `module/core/hotbar.js`).** Every sheet row with a Usar / Atacar / Disparar button becomes draggable (`enableHotbarDrag`, called in both sheets' `_onRender`); dropping it on the hotbar creates a script macro whose whole text is `game.nihility.useItem("<uuid>")`, so it keeps working across system updates. `useItemFromHotbar` resolves the Item and calls the **same** method the button calls — `useSkillItem` / `attackWithWeaponItem` (Personagem) and `useSkillItem` / `fireWeaponItem` (Nave/Veículo), public instance methods the static action handlers now delegate to; Shift at click time (`game.keyboard.isModifierActive("Shift")`) opens the roll modifiers like a Shift+click. The drag uses its **own** type (`NihilityAction`), never the Item drag: dropping a plain Item on another Actor's sheet copies it, which would let a player with two characters duplicate Skills outside the Skill Point economy. Rows that already had an Item drag (inventory, for containers) keep it, and `hotbarDrop` accepts that too. Core lets players create script macros by default (`MACRO_SCRIPT` default role PLAYER); if the GM removed it, the player gets a warning.

**A Skill numa frase (L2, `skills/skill-summary.js` pure/tested + `skill-summary-ui.js`).** Under each Skill's name on both sheets: what it does · where · cost · upkeep ("3d6 de Fogo · cone de 6 m · 20 Mana · Ativa: −3/rodada"). Cost and upkeep go through `effectiveSkillCost` (the level discount), ships use the short energy label, a passive Resistance shows its %, a Skill with Sub-Skills shows only how many. It replaced the old "Custo: X + Y/rodada" span.

## Editor de Skill assistido: avisos, custo sugerido e Modelos (1.81.0)

The owner approved the Design artifact "Editor de Skill Assistido" with all three boards. Board 3 got one extra line on approval: the holder's Mana. Build to the artifact.

The warnings and the suggested cost sit behind `FEATURES.skillAssist`, on by default. Templates are always available.

- **Warnings (L8): `lintSkill(mech, ctx)` in `skills/skill-lint-rules.js`** (pure, tested). It is the Validar Mundo for **one** Skill, run while editing.
  - It returns `{code, level: "hard"|"soft", tab: "general"|"mechanic", effect: index|null, text}` and **never blocks saving**.
  - "hard" means it does nothing or does not apply:
    - Periódico on a target that is not Vida/Mana/Casco/Integridade;
    - Escudo mantido on a Skill that is not Active;
    - a Custo por rodada on a Skill that is not Active;
    - an area or Zona of size 0;
    - Mecânica Dano without a formula, or with an invalid one (`Roll.validate`);
    - Mecânica Efeito without any Efeito;
    - an Efeito with value 0 and no Condition;
    - a Condition, element or Structure that no longer exists in the catalog;
    - a cost above the holder's max Mana;
    - a ship target on a "Si mesmo" Skill of a Personagem, or the reverse.
  - That last check covers only "Si mesmo": a crew member may legitimately aim a ship-target Skill **at the ship**.
  - "soft" means "confira": no duration outside an Active Skill (lasts forever), an Active Skill with no upkeep, or Dano Absoluto together with Dano Mágico.
  - Where they show:
    - on the Skill sheet, through the `nihility.skillWarnings` partial, at the top of the Geral and Mecânica tabs, with "ver ↓" (`scrollToEffect`);
    - as a count on the tab (`tab.warn`);
    - as a line under the effect card (`eff.warnings`, `warnLevel`);
    - in the quick editor, as a box (`warningsBoxHtml`) recomputed on every change through `readSkillEditorForm`.
- **Suggested cost (L9): `suggestSkillCost(mech, ctx)` in `skills/skill-cost-rules.js`** (pure, tested).
  - It adds up "power points" and converts them through `skillCostManaPerPoint`, a world setting in Regras da Mesa (default 0.9). The points come from:
    - average damage (`averageRoll`) × scaling 1.25 × Dano Absoluto 1.5;
    - effects: value × duration, heal/Escudo by value, a periodic tick × its ticks, a flat amount per Condition;
    - area, by shape and size (`areaFactor`), and Zona, by its rounds;
    - a Structure, by its HP.
  - Percent-valued targets (movement, ship %) count at 1/10.
  - It is the **level-1** cost.
  - It is calibrated so the default Bola de Fogo comes out at exactly 25, and the test requires at least 80% of the archetype Skills to land within 50%.
  - An Active Skill also gets an upkeep suggestion (cost × 0.25).
  - The chip (`costChipHtml`) is green within 30% (`costCloseEnough`) and amber otherwise, with "usar" next to it. The breakdown sits in a `<details>`.
  - The holder's Mana **never changes the suggestion**, which would make the same power cost different amounts. It only adds a line (`holderLine`: % of max Mana and how many uses).
- **Templates (L7).**
  - Catalog: `skillTemplatesData`, with defaults in `NIHILITY.DEFAULT_SKILL_TEMPLATES` (`core/config/defaults/skill-templates.js`). There are 12 templates, grouped Dano/Ajuda/Controle, plus the fixed "Em branco".
  - Read it through `getActiveSkillTemplates()`. Each entry is `{id, label, hint, group, skill}`.
  - `templateSkillData` (pure) fills a new Skill: the typed name and the Tier override the template's, and element, Condition or Structure ids the world lacks are dropped (a missing Structure becomes the first one in the catalog).
  - Where templates are offered:
    - In "+ Nova Habilidade" on the character sheet, as radio tiles with a "Vem preenchido" sentence.
    - In the quick editor, **only for a new Skill** (`offerTemplates` = no `name` in `initialData`). Picking one clicks a hidden "template" dialog button, which closes the dialog and reopens it filled (`openSkillEditorDialog` loops through `__template`).
    - "Salvar como modelo" (GM) on the Skill sheet uses `templateFromSkill`.
  - The list editor is `apps/skill-templates-config.js`, found in Configurações Gerais › Personagem.
